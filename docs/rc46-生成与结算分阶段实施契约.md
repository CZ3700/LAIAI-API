## 2. 固定 runtime、动作和纯解析 API

V1 完整四元组不变。V2 精确四元组为：

| adapter_version | `ark-v3-v1` |
| protocol_contract_version | `video-contract-v1` |
| billing_schema_version | `usd-decimal-v1` |

V2 的唯一新增语义是 Query 生成先提交、财务后提交以及相应晚 usage/冲突规则。它不是 V1 别名。主 descriptor 的动作顺序固定 `create,query,cancel,delete,delivery_refresh`，execution/observation/delivery schema 为 **1/1/1**。不增加 DescriptorVersion 或第五个持久协议字段。

A 提供下列纯 API，旧 Resolve/ResolveActionContract 签名保留：

~~~go

func GenerationSettlementV2() Contract

func ResolveQueryApplication(Contract, uint32) (QueryApplication, error)
~~~

## 4. V1 摘要先固定，V2 来源另有显式摘要

在给 ORM 增字段之前，A 先把 `queryEvidenceDigest` 提取为显式旧投影。顺序、导出字段名、Go 类型和 JSON 编码保持以下 **21 字段**：

~~~text

RuntimeVersion, AdapterVersion, ProtocolContractVersion,
ObservationSchemaVersion, HTTPStatus, Outcome, ProviderRequestID,
~~~

ReceivedAt 转 UTC；AppliedAt/RecoveryDueAt 仍编码为 null，ApplyErrorCode 为空，RecoveryVersion 为0。不能删除这四个归零字段、增加 omitempty、换 map、随 ORM 增字段或反射整个模型。新 phase 任意值不得改变 V1 输出；独立旧实现对非空所有证据字段、nil/0、时区、最大整型和转义正文逐 raw bytes/hash 比较。正文只留在专用测试 DB，不输出。

V2 `settlement_evidence_sha256` 是独立固定 struct canonical 的 SHA-256。最小字段意图为：digest 域字面 `query-settlement-evidence-v1`、org/task/attempt、完整 runtime 四元组、原 BillingSnapshotID、ProviderScopeID、CredentialSnapshotID、Task.ChannelID、Task.Model、固定 UpstreamTaskID/UpstreamModel、CreateRequestID、NoChargeStatuses、选定 kind，以及上述21字段 receipt evidence 的小写 SHA。这些只绑定既有固定事实，不含当前价格、财务净额、可变状态/phase/due/version/code/G时间/AppliedAt。域字面只用于 hash 域隔离，不是第五协议列。

A 在底座交接时给出该私有 struct 精确字段/JSON 顺序及独立黄金，再由 B/C 使用同一实现；没有模型直序列化或两份算法。缺失值与显式0、不同原始证据、不同固定上游/快照/合同必须产生不同来源身份。hash 相等不代替 decoder、归属和 no-charge 决定验证。

## 5. 当前锁、phase、pin 和财务屏障

公共协调器仍用 Task→State→**零值 current QueryReceipt** 当前锁读；requested 只提供精确三列定位，不能作为已授权 token。先核完整 Task/snapshot/receipt 合同、AppliedAt 和 NULL 屏障，再在同事务分派 V1 或 V2；不能先在锁外读 runtime 后另开事务。V1 的 tombstone/stale/financialFinal 短路只能留在 V1 Tx 实现。

| 持久形态 | 行为 |
| --- | --- |
| V1 | 原 atomic；不凭四个新字段推断 V2 |
| V2：G时间NULL、kind/digest空、AppliedAtNULL、due非NULL | G；候选另要求due已到，直接应用仍按原调用契约 |
| V2：G时间非NULL、kind为usage/provider_nocharge、AppliedAtNULL | 仅 B；须 State pin 精确等于本AttemptID、due已到、无task财务屏障；digest完整性在当前锁内验证 |
| V2：kind=none | G时间与AppliedAt同一次commit；本条无资金动作 |
| 任意NULL due | 自动消费屏障；新回执、旧token或重启不得解除 |
| 未知/混合runtime、非法phase | 不猜默认、不套V1、不退款；排候选并可观测，direct当前锁拒绝 |

G 完成需 version+1、G时间=主库UTC；若产生 B 待办，due=同次主库UTC、AppliedAt留NULL。B 完成再 version+1、AppliedAt落地。完成、退避及隔离均依 org/task/attempt + 原version + phase + 当前NULL/AppliedAt条件 CAS；拒绝溢出。G token 的晚诊断不能写 B 阶段。只有确认 COMMIT 后才能计 Applied/Review/Deferred。

pin 首次固定，不因同内容新 receipt 替换。原 pin 已 NULL review 时，后来相容 receipt 可完成自身，不能重开 pin 的 due/version。无 usage 的 succeeded 不选 usage pin；后续同目标同终态合法 usage 可选源，包括旧 sequence 的晚证据，但不能倒退生成/交付。

直接重入 `applyQueryReceiptProgress` 在当前锁内见到合法的 settlementV2 待办时返回 Noop，由独立 B 接续；不得执行 B、重取 G 诊断 token 或修改 due/version。NULL review 仍按原屏障返回错误，已 Applied 仍为 Noop。

**task 财务屏障固定闭码为 `query_financial_conflict`。** 仅当前锁内同 org/task/固定上游、可解释 V2 证据证明终态、用量或无费决定矛盾，或与真实 initial 不相容时写入；无 pin/已有 pin 均覆盖。保留原证据，未结算 hold不动；已有 pin/current冲突receipt按各自版本保留review。普通 `settlement_conflict`、unknown、暂态、普通needs_review不自动升级为task屏障。

发现屏障只按同org/task+闭码，**不先过滤 runtime/schema/digest/phase/pin/AppliedAt/due/target**。G/V1联合候选与B候选均在LIMIT前使用索引 EXISTS/NOT EXISTS，避免已关闭task的其它receipt反复占满有限批次；协调器在V1/G分派前以及B事务内均做当前读。新闭码对后来被损坏成V1的task仍阻断自动生成/资金处理，不改变正常V1或普通`settlement_conflict`含义。已标闭码的行后来损坏也必须保守阻断，不能变成“未发现”；未标闭码的未知格式本身不是task屏障。发现任意一条足够阻断，无须无界读取所有正文；实际索引计划必须验证。Task锁串行本task所有pin/冲突/资金决定，若需锁当前和原pin两个receipt，始终先持同一Task/State，不能跨task反向获取。

必须保留反例：succeeded缺usage→无pin/pending_usage→同目标cancelled冲突→后来succeeded+usage。最后一条不得自动扣款。不存在解除API、通用unpause或仅测试调用的假权限入口。

## 6. G 与 B 各自的一次事务

### G：生成先提交，资金原封不动

真实调用方仍为 `pollTask → applyQueryReceipt` 和 S1 query recovery。C在同一当前锁事务中调用 V1原Tx块或V2 G；G提交后不同步调用B、不以内存channel保存唯一待办。

1. 完整固定身份/格式/phase/token检查后，用现有schema1 decoder读取原证据；unknown/404/HasError/不可信目标不产生无费或usage授权。
2. 合法生成推进保留当前状态规则、固定交付引用、QuerySequence/lease所有权和资产终态处理。资产租户锁必须在任何Key锁之前；晚sequence不能回退Task/交付，但不提前完成掉有价值的晚usage。
3. 生成Task/State、生成event/outbox、G phase及首次pin同事务。只有真实生成变更才追加其生成事件，不在B重发。G不写Task.ActualTokens/CostUSD、State的最终账务用量投影、Invocation成本、Key used、hold/account/quota/ledger/BillingEntry；用于财务决定的原用量留在不可变receipt，已有adjusted投影保持。
4. succeeded缺usage保持pending_usage，kind=none、本receipt可完成；显式0属于usage。合法usage待B时从pending_usage转reserved，避免额外GET驱动本地结算。合法原NoChargeStatuses终态且原usage规则成立才固定provider_nocharge；B前不提前released。已有财务final不被改回reserved。
5. 遇终态/用量矛盾按§5保留task屏障。实施收口：G不调用initial reader、不取得Key锁；原pin的不可变观察或无pin的既有生成终态用于判定生成证据矛盾，不能把已调整的Task/State财务投影当initial。无pin而当前可信观察能选源时，即使State已有financialFinal也可固定首pin，但保留全部既有财务投影；真实initial比较统一由B执行。这样资产释放与Task/State生成、生成event、phase/pin始终一次完整提交，B之后发现initial不相容只保留已提交生成并写财务核对，避免在G中只释放资产却未推进生成。生成证据本身的矛盾须在任何资产/生成写入前处理。
6. 最后读取主库时钟并原子写phase；失败回滚生成/phase/event，独立持久的raw receipt保持。G继承原调用方ctx：S1 lane现为2秒，poll调用沿原ctx，不为保持V1兼容擅改其整体期限；新clock≤200ms、诊断≤1秒且继承剩余。

### B：所有资金、投影和完成标记一次提交

1. 独立零网络入口按Task→State→零值pin receipt当前锁，复验完整合同、原snapshot/target、pin、phase/version/due/AppliedAt、digest和task屏障。不得取凭据、解密执行胶囊、GET、刷新链接或读取当前报价。
2. 同tx读取真正initial事实，保持Key→Snapshot→initial当前锁顺序。不能把RR旧快照的absence或当前adjusted投影当初始事实。
3. absent：原 `SettleUsageTx`/`ReleaseConfirmedTx` + 原quota→ledger→Key→initial写序 + Task/State账务投影 + 必要Invocation + 稳定billing事件/outbox + receipt完成，全部在本次财务事务。原金额/price/FX/超hold规则不变。
4. compatible：仅完成本receipt进度，不调用资金写原语，不覆盖调整后的Task/State/Invocation，不重复账务事件。initial100→已审adjust90→B100仍保留90。
5. conflict：保留initial与新证据，写§5闭码核对，不调用资金写原语。不同合法source但同tokens可相容；nil≠0。旧released的not_dispatched不能与provider_nocharge互认，`ReleaseConfirmedTx.Replay`本身不证明同reason。
