# G2-A2 官方视频目录与报价规则实施契约

2026-10-26，主控已批准本批实施，正式架构已先于代码更新。范围：`/v1/video/models` 保留诊断字段与配置行；`/v1/models` 的官方段只收录至少一项可用动作；legacy 范围兼容，grouped Key 认证、签发继续关闭。主控已确认 G2-A1 PR69 合入 main `7bb78dc84320dddb3ec18741be46e33bfefab069`。A2 使用独立工作树，文件分工由主控执行；实施时的假设及失败轮保留，后续验收单独记录。

本契约采用一个可真实消费的 PR，不先合入一个无人调用的抽象授权服务。主体、渠道、价格 reader 可以分提交开发，但至少两个目录入口和现有 `plan` 规则接线、独立验收一起达到合入条件。本批不引入 migration、不修改 worker/回执/账务状态机、不开放视频 BYOK。

## 1. 交付与明确边界

实际消费入口：

1. `server.listPricedModels`：`GET /v1/models` 官方视频段。
2. `video.HandleModels`：`GET /v1/video/models` 的诊断目录。
3. `video.plan`：`EstimateForKey` 和真正新受理的 `Create` 共用发布规则；金额仍由 `ResolvePricingTx` / `QuoteWithMinimumTx` / `ReserveTx` 计算和复核。
4. `server.loadVideoPricingProjection`：营销价格投影复用相同纯规则，但不进入 Key/Org 动作资格分支。

首批可发布的公有名严格是 `seedance-2.0`、`seedance-2.5`、`seedance-2.0-fast`、`seedance-2.0-mini`，大小写精确。上游部署名不是入口别名；不得自动补 seedance1 或新的 2.5 变种。每个官方模型只能使用当前 `ModelConfig.ChannelID`；不能因为其他渠道也有同名模型就改绑或回退。官方路径要求平台渠道 `OwnerOrgID=0`，保留现有两个 provider spelling `volcengine` / `modelark`。

目录资格是**当前观察到的模型级结构资格**，不承诺任意请求可执行。它不检查余额、实时并发、RPM、供应商剩余额度、具体素材与真人授权、网络健康、凭据能否解密或上游实际接受。它不是发送许可、预算预留、授权缓存或完整策略版本向量。`eligible=true` 不能取代 Create、Gate、Reserve 和最后发送前已有校验。

G2-A1 的候选层仍只证明组成员关系。生产 Key 入口本批继续通过 `VerifyKey`，因此 grouped Key 根本不能进入新目录。内部“候选 ChannelIDs 与固定 cfg.ChannelID 相交”的组合测试可以调用真实 A1 reader，但**不添加能够在生产开启 grouped 的环境变量、测试后门或成功动作结果**。本批不为四模型目录而循环调用 A1 七查询解析器四次；后续开放 grouped 前再提供经审核的批量组合入口。

## 2. 两类发布状态与动作资格不得混为一谈

发布状态不含 Key/Org 因素，只由模型配置、固定渠道身份、作用域、有效价目、最低用量规则确定。动作资格在发布结果之上加入当前主体和 scope；结果不能因“有价格”自动变成 create 许可。

### 2.1 `/v1/video/models` 的兼容形状

保留顶层 `data` 和原有行字段：`id/enabled/verified/capability_version/pricing_version/billing_rule_version/capabilities/prices`。保留已登记、且在当前 legacy Key 模型范围内的配置行，包括 disabled、未验证、缺价格的配置。不存在配置不合成默认行。

原 `capabilities` 字段均保留；新增 `min_duration_seconds`、`ratios`，值来自已验证的 capability，不能把配置格式错误当成完整能力。原 `prices` 的元素 JSON 形状保留，但只收录本批共同校验通过的组合，排序固定。冲突或不完整组合不再以普通可用价格对外返回，原因放在新增诊断字段。金额全部为 USD Decimal 字符串；此 API 不跟随展示币种改变计费单位。

### 2.2 状态定义

- `publication.status=published`：能力允许的有限组合全部通过校验，至少一个组合。
- `partial`：至少一个组合可用，同时有能力允许但尚未发布/无效的组合。
- `blocked`：零可用组合；配置行仍返回。配置错误时组合可以是空数组，不猜能力矩阵。
- 每个组合只用 `published/blocked`。不把 capability 不允许的无限枚举全部造出来；仅列共同纯函数生成的有限当前能力矩阵。

`enabled` / `verified` 保持原义，不能改成 publication 或 action 的别名。配置 disabled 时仍可描述原有能力，但组合全部 blocked。

### 2.3 `/v1/models`

保留 OpenAI list 外形 `{object:"list",data:[{id,object:"model",owned_by}]}`；不给普通 SDK 强塞渠道/组/成本字段。官方四模型只有在新目录中至少一个 `actions.*.eligible=true` 才加入。输出固定公有名、去重、按现有排序；不能从通用 `model_prices` 或其他同名渠道补回被官方判断排除的模型。

该“至少一项”不是诊断路由有权访问：`models_read` 动作也要求至少一个已发布组合。因而 read Key 可发现有价、可解释能力的模型，完全未发布模型只在 `/v1/video/models` 诊断页出现。

## 3. 主体、scope 与 legacy 兼容

只接受宿主认证后拿到的 OrgID/KeyID 引用，不接受用户请求中的 mode/group/版本/entitlement。目录同一只读事务复读主库 Key、Org/成员状态与 entitlement。主体现已失效或模式非 legacy，整个调用拒绝，不为其返回配置诊断或退回营销列表。未知模式/损坏事实绝不解释为 legacy。

legacy `ModelLimits` 仍按现有 `AllowsModel` 精确语义：整体 TrimSpace 为空表示不限制；逗号拆项并 TrimSpace 后精确匹配；不改成大小写不敏感、glob、upstream alias 或默认组。不要通过构造缺字段的 APIKey 调用 validLegacyRouting 碰巧成功；提取 identity 所属的共享纯判定，原 AllowsModel 也委托它，或使用完整已验证 DTO 显式校验。

| 动作/入口 | scope | 是否要求已发布组合 | FeatureVideo / video_org_policies |
| --- | --- | --- | --- |
| `GET /v1/video/models` 路由本身 | `video:read` / `video:*` / `*` | 否，诊断行可 blocked | 不要求开通生成，保留当前可诊断性 |
| `actions.models_read` | 同上 | 是，至少一个 | 不要求；只说明已发布模型能力可查询 |
| `POST /v1/video/estimates` / `actions.estimate` | `video:write` / `video:*` / `*` | 是；实际请求还需命中具体组合 | 保留现状，不新增 FeatureVideo/异步开通前置；报价无任务/冻结 |
| 新建 `POST /v1/video/generations` / `actions.create` | 同上 | 是；实际请求命中具体组合 | FeatureVideo=true，明确存在且合法的 Policy.AsyncExecutionAllowed=true，RetentionDays 1..30 |
| `GET /v1/models` | 保持现有发现路由认证方式 | 官方段按上述至少一项动作 | 不替通用段新增 video scope |

`video:*` / `*` 的逗号或空格拆分规则沿用 `hasScope`。空 scopes 不自动获得视频权限；read 不推导 write，write 也不推导 read。因此 write-only Key 不能直接访问 `/v1/video/models`，但可以通过 `/v1/models` 发现 estimate/create 可用的模型；read-only Key 可诊断价格而不能估价或创建。

IP：`/v1/video/*` 保留 Middleware 的实际 IP 校验；本批不借目录重构改全站发现接口的既有 IP 策略。`/v1/models` 当前没有 `AllowsIP` 校验，必须明确这是存量发现行为，不能声称这次已经统一所有认证因素。返回结果不代表该 Key 在当前客户端 IP 有执行许可。

未配置 entitlement 使用现有 DefaultEntitlements；真实 SQL 错误不得当默认开通。Policy 缺行对 create 是关闭，**不能用素材 shared-default 的 AllowAsync 替代视频 Policy**。估价保持现状，但其目录动作说明明确不代表生成已开通。

## 4. 稳定原因码与错误分类

以下是客户可见的诊断码，不附内部实体 ID、credential、scope account/project、原始异常。同层多个原因按表序输出；底层前提缺失时停止依赖它的推断，避免同时编造“最低规则缺失”等次生错误。

| 顺序 | reason code | 范围/含义 |
| --- | --- | --- |
| 1 | `unsupported_model` | 已登记但不是四个正式公有模型的诊断行，不进入公共发现 |
| 2 | `model_disabled` | cfg 或 capability 明确 disabled |
| 3 | `capability_unverified` | cfg 未核验或 capability 未 verified |
| 4 | `capability_invalid` | 版本、JSON、默认值、上下游绑定、边界或能力矩阵不合法 |
| 5 | `provider_binding_unavailable` | 固定 scope/channel 缺失、禁用、非平台、厂商/官方 endpoint 不匹配；不暴露具体内部原因 |
| 6 | `pricing_missing` | 该能力组合无当前有效规则 |
| 7 | `pricing_conflict` | 同一组合有多条当前有效规则，跨版本也算冲突 |
| 8 | `pricing_version_mismatch` | 唯一规则不属于 cfg.PricingVersion |
| 9 | `pricing_invalid` | 费率、成本基准、风险系数、公式、FX 等内部发布事实不合法，只暴露此总码 |
| 10 | `minimum_coverage_missing` | 参考视频最低规则缺失或覆盖不全 |
| 11 | `minimum_rule_invalid` | 已有最低规则身份/来源/重复 cell/数值不合法 |
| 12 | `publication_unavailable` | 动作因本模型零 published 组合不可用；具体原因看 publication |
| 13 | `scope_missing` | 该模型级动作缺 scope |
| 14 | `video_feature_disabled` | 仅 create，组织 FeatureVideo 关闭 |
| 15 | `video_execution_disabled` | 仅 create，Policy 缺失/关闭 |
| 16 | `video_execution_policy_invalid` | 仅 create，持久 Policy 内容不合法 |
| 17 | `credential_unavailable` | 仅 create，固定渠道没有符合既有选择规则的非空凭据元数据 |

Key 模型白名单外的行直接不返回，不返回 `model_not_allowed` 行以泄露目录。当前 Key/Org/成员失效是整个请求鉴权拒绝；grouped 模式继续 401/403，不返回一个 `grouped_mode_disabled` 可用列表。

DB 错误、超时、依赖丢失、非真实 Tx、数据量超上界均是整个请求错误，不降级为 blocked 行、空 prices 或 `data:[]`。内部固定 sentinel 固定为 `ErrCatalogInvalid/Denied/Limit/Unavailable`；保留 `errors.Is(context.Canceled/DeadlineExceeded)`。`/v1/video/models` 走已有安全 error envelope，503 对外 `provider_unavailable`；`/v1/models` 保留现有 relay envelope/type，503 固定 `model catalog unavailable`，不回显原错。空合法配置/白名单结果仍是 200 空数组。

```go
// PublicationContext 完整定义在同目录领域接口契约；含 Frames 与合法帧数范围。
func ValidatePublishedRuleTx(ctx context.Context, tx *gorm.DB, rule PricingRule,
    expectedKey PricingKey, expectedVersion string, p PublicationContext) error
```

一次读取所有相关 scope/model 的当前有效 enabled rules，**包括其他版本以识别 overlap**；不能先只 WHERE version=cfg.version。查询成对限定，不用四个 model 与四个 scope 的笛卡尔组合读无关行。返回后 Go 精确核对模型、版本、组合字段，防旧 collation 大小写/PAD SPACE 混入。

第二条读取实际 input-video rule 引用的 minimum sets；第三条读取这些 sets 的 cells。来源/重复/覆盖校验留在 videobilling；普通 HTTP DTO 不包含 SourceURL/EvidenceHash、SupplierCNYPer1M、scope/预算/FX。复用 `CatalogMinimumTokens`，如需区分 missing/invalid，在本域返回固定分类，不复制最低规则算法到 video。

发布资格需同时验证：合法正客户售价/成本基准、风险系数>=1、有效公式/版本、合法 FX 事实、每个允许 ratio 的计量边界可由现 `Quote` 表达、参考视频完整最低覆盖。Quote 的探针只做配置合法性验证，不能把“最大时长探针金额”当真实报价，也不能用 probe 替换具体请求的 QuoteWithMinimumTx。

同域提供上述 `ValidatePublishedRuleTx` 给 `plan`，精确核对 expectedKey 全部键字段与 expectedVersion，复用同一纯校验和完整 minimum coverage；其额外 SQL 最多2条（set/cells），可复用本次已读数据，不能给每个 ratio/duration 发 SQL。保留 QuoteWithMinimumTx 与 ReserveTx 里的精确实际请求复核，不改私有 minimumSelection/HMAC/快照算法。

`PublicationContext` 新增 `Frames bool` 与 `MinFrames/MaxFrames/FrameStep int64`。非参考视频先清除旧 MinimumTokens，再用 duration、合法 frames 两种互斥 MeteringInput 分别 Quote；帧数探针用 MaxFrames 以内实际可达的最大步进值，计算前验证正范围和乘加不溢出。参考视频仍遵守现有 QuoteWithMinimumTx 的 duration-only 限制：仅校验完整 duration 最低覆盖，不因 cap.Frames=true 把合法 duration 组合整组 blocked，也不开放 reference frames。发布资格不能宣传为所有 frames/输入组合都受支持。

## 6. 只读快照、上界和故障语义

### 6.1 官方目录事务

使用主库 `sql.LevelRepeatableRead + ReadOnly:true`，固定一次可信 `at`，在第一条一致读之前建立；无 TTL/只读副本。所有新 reader 接收相同 tx/context，不 Begin、不锁 UPDATE、不换连接。

共同期限 **1秒**，含取得连接/Begin/所有查询/计算/Commit；单 SELECT 子期限 **≤200ms 且不超过剩余期限**，MySQL hint 取实际剩余毫秒。子期限只覆盖数据库执行和Scan，检查该次查询的context后即取消子context；CPU解析/组合继续受共同父context约束，不让已经完成的SELECT子期限误杀后续解析。取消返回零值结果；不能在父 context 失效后仍交付已拼好的半页。新 Session 一次设置 `NewDB:true, Context:child, Logger:Discard`，清 Where/Order/Limit 污染但保留 ConnPool。支持真实 MySQL 和快速 SQLite；DryRun/非真实 Tx/坏依赖拒绝。

本批官方段业务 SELECT 上界 **15**，按以下计划计数；没有按模型 N+1：

| 域事实 | 最大 SELECT | 行/字节边界 |
| --- | ---: | --- |
| 主体/Org成员/entitlement | 3 | A1现有单主体3条；各受限字符串投影 |
| video configs | 1 | LIMIT65，最多64诊断行；仅4 canonical 深入解析；cap/bounds各≤64KiB，累计≤1MiB，先受限投影 |
| ProviderScopes | 1 | cfg四模型对应ID，最多4 |
| video Policy | 1 | 单Org PK，缺行有明确语义 |
| 固定渠道摘要+凭据 EXISTS | 1 | 最多4行；EXISTS使用channel_id索引 |
| 活跃 rules / minimum sets / cells | 3 | 分别 LIMIT257 / LIMIT17 / LIMIT32001；最多256 rules、16 sets、32000 cells |
| identity计费组 / relay倍率 | 2 | 单Org +最多4模型；采用上一节单SQL倍率方案 |
| portrait辅助路由 | 3 | 见下段，不能调用现 assetScopeTx 四遍 |
| **总计** | **15** | 不是“继承A1的7条” |

超上界整体 ErrCatalogLimit，不截断成已发布；这些是读保护边界，不随手修改管理侧配置限额。配置JSON累计1MiB是完整结果接受门槛，不是查询期间网络/内存绝对上界；受限投影仍可能先传输至多65行各两个64KiB字段，再拒绝超累计量，实施必须如实记录这一有限最坏值。计数不包含宿主已有 VerifyKey、视频请求 Invocation 审计；报告必须把它们分开，不声称整条HTTP只15条SQL。

portrait 三查询上界：先一条查询取得当前Org是否存在任意显式route（EXISTS可作为投影）以及四个固定scope的显式route有限行；若存在任何显式route，包括disabled，则绝不落回 shared-default。无显式route才查shared singleton。最后批量读选中 `(scopeID,version)` 的管理配置安全列（不读credential）。provider facts与Policy使用已读结果；只取capabilities中Portrait及精确account/region/project一致校验。可将 EXISTS 与有限route 查询写成单个派生表/LEFT JOIN，但不得因查不到四个scope的route就漏掉“其他scope显式route阻止继承”的规则。合法缺失false，SQL错误error。不得在此改素材服务、上传或shared default写入。

### 14.1 唯一拟改读取：先 LIMIT，再完整聚合

前两条 rules / minimum sets 查询及其256 / 16上限保持不变。仅第三条 cells SQL 改为以下固定形状；表、别名、列、聚合函数及LIMIT由本域常量提供，只有已经精确验证的最多16个 rule_set_id 作为参数。

```sql
SELECT /*+ MAX_EXECUTION_TIME(remaining_ms) */
       COUNT(*) AS cell_count,
       JSON_ARRAYAGG(JSON_ARRAY(
           id, rule_set_id, resolution, ratio,
           output_duration_ms, fps, minimum_tokens
       )) AS cells_json
FROM (
    SELECT id, rule_set_id, resolution, ratio,
           output_duration_ms, fps, minimum_tokens
    FROM video_minimum_rule_cells
    WHERE rule_set_id IN (parameterized_ids)
    ORDER BY id
    LIMIT 32001
) AS bounded_cells
```

这是读取同一批原始事实的传输格式调整。不得使用DISTINCT、GROUP_CONCAT、合法值WHERE、CASE截断字段、分组挑选、预先去重或其它只留下可发布cell的条件；全部七列包含原ID和归属，无metadata或最低覆盖字段省略。COUNT与JSON必须对同一个派生表计算，不能另发COUNT或分批查询。MySQL聚合元素顺序没有保证，消费者不能依赖JSON数组顺序选取赢家；如需要内部确定顺序，只能在父期限内按ID排序，不能隐藏重复或坏事实。[MySQL聚合函数文档](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html)

依然使用调用方真实RR事务、原ConnPool与context，不另Begin、不换库、不加缓存、不重试SQL。业务账务域最多3条、官方段最多15条、SDK总最多18条SELECT，所有实际SQL及参数继续由真实Query/Row观察器捕获并EXPLAIN。ValidatePublishedRuleTx使用相同最低规则读取与decoder，不建立第二份发布算法；实际Quote/Reserve、minimum selection/HMAC及金额公式不改。

### 14.2 期限、物理行与观测口径

聚合查询创建子context的时点与§6保持一致，单条最多200ms且不超过父剩余期限，MySQL保留MAX_EXECUTION_TIME。SQL执行、打开rows、Next、Scan两个聚合字段、检查多余物理行、Err、Close及子context最终检查全部在此窗口内。正常聚合恰好一行（空集也一行）；零行或多行作为完整性错误。Rows返回打开结果同时附带错误、Scan/Err/Close失败和取消均关闭结果后安全失败，不能解码已有半包。

只有rows已关闭且本次子期限检查成功，才能取消该子context并用原父context解码JSON、校验归属/最低覆盖和组装快照。目录原1秒包括这些工作及Commit；解码必须在开始、逐tuple及结束检查父context，不能只在SQL后检查一次。不得另给JSON解码1秒，或通过goroutine继续无期限解码。plan的非目录调用仍使用§7原caller期限，不新增目录1秒限制；单条200ms不变。

`RowsAffected`只计实际遍历的物理行：正常值为1，不能写成32000。另外保留本次真实`cell_count`和实际成功解码数量供测试观察；完整成功必须后两者一致，相等本身不代表成功（例如尾随错误或最后一项后父取消仍返回零快照）。不得用COUNT预期值冒充已经读取/解码的事实，也不得在Row.After打开结果时就宣称扫描完成。业务日志仍不输出原SQL、参数或JSON；测试仅对合成数据保留完整SQL/Vars、ConnPool、打开/完成耗时、物理行数、cell_count和解码数。SDK18条断言按实际SELECT次数，不能将聚合内部派生表另算一次，也不能漏算它。

### 14.3 共同精确decoder与失败边界

decoder只能接收已完成的聚合行，不访问数据库。按下面顺序验证，任一步失败均返回零快照，不交付已解析cells：

1. COUNT必须是非NULL精确整数且在0..32001；负数、溢出、非整数或更大值都是不可信聚合结果。SQL NULL与JSON值`null`有区别。count=0时仅接受该dialect明确的空集表示：MySQL SQL NULL或合法空数组、SQLite合法空数组；正count的SQL NULL/JSON null不得归为空集合。
2. 原始JSON字节长度必须不超过§14.4的接受门槛，检查有效UTF-8。正数量只能为外层数组；tuple必须恰好七项且不能为NULL，字段NULL也拒绝。不得用通用`[]interface{}`经float64转换；用受限逐tuple解析和原始数字token（或UseNumber）直接ParseUint/ParseInt。两个ID保留完整uint64，duration/FPS/minimum_tokens保留完整int64；禁止小数、指数、带引号数字、溢出或其它宽松强转，特别覆盖2^53以上的精确值。
3. 字符串必须是JSON字符串，解码不允许无效UTF-8或不成对surrogate被静默替换；按生产VARCHAR(16)物理宽度核验码点数。只做物理形状校验，不在这里将负值/未知resolution等业务坏事实改成合法值或筛掉，仍交既有minimum纯语义分类。集合归属继续精确验证RuleSetID，不能读到别的set后静默丢弃。
4. 对可接受count≤32000，实际tuple数量必须与COUNT完全相等，结束后只能有JSON允许的空白并立即EOF；缺尾、额外tuple、尾随第二个值、截断、tuple字段缺失/多余均拒绝。避免对整个文档或任意长tuple建立无界generic数组，解码最多32000个接受对象。不能只将tuple Decode进Go固定`[7]json.RawMessage`后假定长度已被验证，encoding/json会丢弃多余数组元素；必须显式验证恰好七项。count=32001已明确证明超限，可直接返回既有ErrCatalogTariffLimit，不必为确定拒绝的结果解码全部tuple；不能把它截断成32000成功。
5. 有效空集仍走既有缺覆盖语义；物理结构/SQL/身份损坏返回安全ErrCatalogTariffUnavailable，数量或接受字节上界返回ErrCatalogTariffLimit，取消/超时保留现有errors.Is能力。每一种错误的Error文本都不含JSON、原SQL、驱动明文。读取失败不退回逐行、旧价格或空快照成功。

MySQL JSON_ARRAYAGG空集返回NULL，不可无条件COALESCE将正数量异常伪装空数组；是否空集以同一行COUNT核对。[MySQL聚合函数文档](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html)

### 14.4 从生产列推导字节与包预算

0111真实schema固定为两个BIGINT UNSIGNED、三个BIGINT、两个VARCHAR(16) utf8mb4；没有放宽DDL。两个整型ID和三个有符号整型各最多20个ASCII十进制字节。每个字符串最多16个Unicode码点；对有效码点按最坏UTF-16双surrogate的12字节JSON转义保守计费，再加两个引号，即每列至多194字节。七元组的五个整数100字节、两字符串388字节、方括号2字节、六个逗号及各一个空格12字节，合计502字节；外层每元素再预留逗号和一个空格，至多504字节。为固定分隔符保留可核算余量，常量取512字节/tuple，加外层2字节：

`maxCatalogMinimumJSONBytes = 512 * 32001 + 2 = 16,384,514 bytes`。

512来自上述504向上取整，不能把它作为不受schema约束的任意大JSON承诺。此推导绑定数据库JSON函数产生的正规输出；不是对任意用户JSON空白格式的上界。MySQL文档说明其规范化输出在逗号/冒号后插入一个空格；当前固定MySQL版本还必须通过真实极值实验确认整数、Unicode/转义与输出字节数，不能仅凭公式宣称验证完成。[MySQL JSON规范化文档](https://dev.mysql.com/doc/refman/8.0/en/json.html)

第三读只有COUNT与JSON两列。对本上限，二进制行的头/null bitmap、8字节COUNT及长度前缀合计至多19字节；文本行的COUNT和长度前缀也在此内。再计4字节packet header，以32字节作为两种协议的保守行封装预算，得16,384,546字节；按MySQL配置1024字节粒度向上取整，测试/部署的服务器`max_allowed_packet`至少16,385,024字节。此下界在独立环境预检中读取并记录安全数值，不增加业务第4条SELECT、不静默SET服务器变量或改全局DSN。现有驱动配置如更小或不能满足实测协议要求，必须明确环境不符合条件；不能为得到绿灯临时放宽业务期限或数量。

上述上界是可接受JSON及单行协议预算，**不是Go进程峰值内存或入站分配的绝对上限**：go-sql-driver/mysql v1.8.1的readPacket不按MaxAllowedPacket检查入站大小，该字段用于writePacket；Scan/driver/JSON解析可能同时保留缓冲与目标slice。MySQL的过大包会产生连接错误，必须整请求失败；本方案不能把低包限制误记为缺价、截断JSON后成功或悄悄自动重连重试。单行属于通信packet的事实见[MySQL包大小说明](https://dev.mysql.com/doc/refman/8.0/en/packet-too-large.html)。真实MySQL极值实验须记录实际格式/包配置/峰值观测边界，尚不构成500并发或完整容量证明。

真实低packet负例只能在独立连接及允许的私有测试设置中进行，不SET GLOBAL影响共享数据库。若当前MySQL版本不允许session修改该变量，应明确记录该边界并另申请隔离小容器验证；注入NULL/驱动错误只能证明decoder/错误传播，不能冒充真实packet限制实验。所有正常矩阵保持既定环境，不以增加包限制掩盖传输格式或数据量错误。
