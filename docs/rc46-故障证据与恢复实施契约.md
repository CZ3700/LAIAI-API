## 1. 首要目标和批次边界

首先修复已经收到的上游响应因 Operation CAS 失败而一起回滚的问题。迟到执行者可以保存其真实 attempt 的证据；只有当前受支持、拥有有效写权限的恢复者可以推进任务和资金。证据保存成功、状态应用成功、结算成功是三个不同事实。

| 批次 | 交付范围 | 不在该批完成的内容 | 完成门槛 |
| --- | --- | --- | --- |
| P0-2A | 固定 attempt 归属、独立响应收件箱、操作与交付查询证据保存、兼容恢复入口 | 不调高并发/QPS，不缩短现有租约，不拆独立 Worker，不改变扣费公式 | CAS 失败、任务删除、版本暂不支持都不能回滚已经成功持久化的证据；无第二次创建/删除 HTTP，无自动退款 |
| P0-2B1 | 主库时间、可续租的执行权限与 fence、查询/取消/删除乱序控制 | 不接 Redis 新速率算法，不发布 500 在途承诺 | 主机时钟偏移不改变领取/续租/失效判断；旧 fence 零状态/资金写入；新持有者可消费旧 attempt 证据 |
| P0-2B2 | 从已存终态证据独立推进结算、配额和 Outbox，补齐崩溃恢复 | 不新建账本，不把日志金额当实扣，不修改客户价格和授权上限 | generation 已终态但 billing 待处理可独立恢复；同证据重复/多进程消费只出现一次初始资金动作 |

P0-2A1 先实现创建响应的独立保存、应用和恢复及真实 MySQL 故障验收；紧接 A1.1 补齐保存重试、派发熔断与关机等待；P0-2A2 再覆盖取消、删除、交付补查和完整兼容演练。以上批次默认不开启新写入，A1.1 与 A2 均为启用门槛。P0-2B1、P0-2B2 分开评审和提交；前一批通过后再进入后一批。不能只上线新表就宣称闭环。完整 R3 验收需要 A1/A1.1/A2/B1/B2 均完成。

P0-3 才负责独立 Worker 拓扑、并发池、统一容量占用和公平调度。本文只规定未来调度必须遵守的故障与一致性契约。

## 3. 三类结果必须分开

| 结果 | 可成立的依据 | 允许推进的动作 |
| --- | --- | --- |
| 已受理 accepted | 同一 attempt 的受控上游客户端返回可校验的创建成功及上游任务 ID | 当前恢复者校验账号作用域、归属和协议后建立唯一绑定，进入 queued；创建成功不等于生成成功 |
| 确定未发送 not_sent | 在取得“可能发送”许可之前的本地拒绝，或适配器具有可测试证明的未发送结果 | 原固定契约支持且输入格式已核验时，可按原规则释放；不由租约过期、超时或鉴权错误猜测 |
| 明确拒绝 rejected | 已解析的官方拒绝响应，且该固定适配契约证明该错误不产生任务/费用 | 保留证据，按明确的拒绝与计费规则处理；不能只看 HTTP 状态码 |
| 结果未知 unknown | 可能已发送后退出、连接中断、超时、无法解析、证据暂未持久化、无法确认官方结局 | 保留 hold、供应商风险敞口与必要的执行占用，进入核对；不重新 POST，不换渠道，不按时间退款 |
| 解释器不可用 | 固定版本或格式不受当前进程支持 | 保留原状态和证据，等待兼容进程；不得改成 rejected/not_sent |

取消的 DELETE ACK 只确认请求响应，不能证明生成已取消或费用为零。DELETE 后的 GET 404、过期产物链接、查询鉴权失败都不构成退款依据。资源删除与账务历史保留继续分离。

## 4. P0-2A 的数据决定

建议新增以下三个小表，避免把重放进度塞进不可变证据，也避免把 `Operation.Version` 改作另一种身份。名称为评审名，实现前统一核对。

| 表/实体 | 固定字段及唯一性 | 可变部分 |
| --- | --- | --- |
| `video_execution_attempts` | `attempt_id` 主键；org/task/action、Operation ID（查询允许空）、provider scope、credential snapshot 引用、输入引用/HMAC、runtime 四元组、输入/观察格式、初始 Operation 版本、查询 sequence、数据库登记时间 | 固定身份不改写。发送阶段/租约仍由宿主状态机控制，不在该表反复覆盖归属 |
| `video_response_inbox` | `receipt_id` 主键；`UNIQUE(org_id, attempt_id, evidence_hmac_version, evidence_hmac)`；attempt/任务/动作/作用域/生产者契约、HTTP 状态、固定结果分类、上游 request/task ID、加密 payload 引用、数据库接收时间 | 整行作为证据追加后不改写；不含 AppliedAt，不存正文/URL/凭据明文 |
| `video_receipt_applications` | `receipt_id` 唯一且必须关联同 org/task/attempt 的 inbox；已存在行不能换归属 | pending/applied/blocked/review、重试 due、错误分类、应用事件/结算引用；状态按 CAS 推进 |

新表不持有资金数值的权威副本。费用仍由既有 Snapshot、UsageEvidence、BillingEntry、Ledger 和 quota reservation 决定。凭据只保存既有快照引用，响应正文、签名链接仍走 Invocation Store。

`video_query_receipts` 已先持久化后应用，P0-2A 不再复制一份同等权威的查询收件箱。可复用相同的应用接口，但保留其现有唯一键及证据来源。P0-2B 如需增加 query attempt 的固定归属，在原表扩展或关联 `video_execution_attempts`；不得双读两个来源后各结算一次。

三个新表的必要性分别是：证明迟到响应属于哪次已登记发送、保存不会被当前 CAS 吞掉的证据、在不修改证据的条件下记录重放进度。若评审选择合并表，必须仍用字段级不可变约束/接口封装保持这三种语义，不能重新形成“证据插入依赖任务 CAS 成功”的事务。

候选索引至少覆盖应用 `(state, next_attempt_at, receipt_id)`、attempt `(org_id, task_id, action, registered_at)` 和 inbox `(org_id, attempt_id, received_at, receipt_id)`。实际 DDL 和 `EXPLAIN` 一起评审；未知契约、有效租约、不可自动重试的冲突必须在 LIMIT 前排除。没有组织限定的诊断只能做管理员低基数汇总。

## 5. 保存响应与应用响应的事务边界

### 5.1 发送之前

在当前 claim 事务内登记不可变 attempt 身份，绑定 State/Operation 的真实固定值，不能从活动配置重建。事务失败就没有发送许可。`video_attempts` 继续作为阶段审计，不替代身份行。

历史已发送任务不能因为缺新身份行而被认定未发送。新执行者只对自己新登记的 attempt 使用新写入路径；历史回执经 legacy 恢复器处理。能够从既有持久事实严格证明归属的历史 attempt 才能迁入，登记迁入来源；证据不足的任务保留核对状态，不制造发送时间/原始 build。

确定的分流判据是同 org/operation 的不可变执行登记，存储协议固定 `inbox-v1`。legacy 候选在 LIMIT 前用 NOT EXISTS 排除任何此类登记，而非用 ReceiptRef 是否为空推测。新恢复候选精确匹配存储协议、生产者契约和格式；未知登记不回退 legacy。新登记创建与 claim 原子提交，原普通 QueryReceipt 不新增登记。开关只决定新创建 claim 是否登记，恢复不受开关关闭影响。P0-2A1 的无响应过期登记有独立 unknown 恢复，不能重新 POST 或释放资金。

### 5.2 独立追加

HTTP 返回后，写入者使用发送前捕获的 attempt 描述符。追加接口读取不可变登记并精确核对 org/task/action/scope/契约/输入身份，但**不要求当前 Operation 版本、租约或 registry 仍支持应用**。没有登记、跨组织、归属不一致的外部回执不能注入。

在一个独立短事务中写 `inbox + Invocation 元数据/加密 staging + application pending + response_received 审计`。这个事务不更新 Task、Operation 当前版本、hold、quota 或上游占用。Task 已软删除也不删除财务/证据归属。

同一次数据库重试必须使用稳定 evidence HMAC 与同一捕获内容。并发重复追加先由 inbox 唯一键选出赢家；失败者读取并核验已经提交的完整记录，不再次 Stage 一个相同 correlation、不同随机 payload ID 的对象。可先准备加密对象，事务内先占唯一 inbox 键再 Stage；任何步骤失败全事务回滚，不留下未完成引用。禁止 `ON DUPLICATE KEY UPDATE` 覆盖旧正文、生产者版本或上游 ID。

Invocation correlation 必须包含稳定的 receipt 身份：同 attempt 的不同证据不能复用旧的 `request_id=attempt_id` 关联键，否则第二份证据会被 `ErrVideoConflict` 拒绝。实际发送 attempt 保持不变，receipt 身份作为独立请求关联值；同证据重试由 inbox 唯一键返回已经提交的 payload 引用。历史留存关闭时仍保存可恢复的受控结果分类、上游 ID 和契约身份；恢复不能依赖解密历史正文。交付胶囊保留独立用途与留存策略。

同 attempt 的两份相同证据只产生一个 inbox/application。不同证据都保留；本地 transport unknown 后出现可校验的完整响应不自动视为矛盾，恢复器可据实补全。两个相互冲突的确定响应/上游 ID 进入人工核对，不能选择最晚一份覆盖已经结算的事实。

冲突比较先于“Operation 已 confirmed/rejected”的幂等短路。已应用事实相同才能标记等价消费，矛盾证据必须保留并转 review；旧 attempt 与当前另一个可能发送的 attempt 不得自动互相替代。状态事件与 Outbox 由应用行锁和稳定来源身份去重，不因 receipt ID 不同重复制造同一状态迁移。

创建收件箱的 review 是自动状态和账务恢复的隔离屏障，不能只显示提示后由普通 GET 清除。普通查询候选与 QueryReceipt 恢复候选在 LIMIT 前排除，领取与应用事务在 Task/State 锁下再次检查；在途 GET 仍保存其原有 QueryReceipt，但不应用、不自动扣费/解冻、不覆盖原绑定或核对状态。既有终结资金不回滚；恢复隔离需明确核对，不能用时间、重启或开关变化代替。

非 JSON、截断或过大的响应必须保留安全的结果分类与有界证据，不能因为 JSON Marshal/解码失败就默默丢掉“可能已发送”事实。现有 Invocation Prepare 的格式限制要在实施时实测；若增加原始响应封装，必须使用独立受控格式、保留密钥擦除规则和解密审计，不能把任意正文放进业务表或 stdout。

### 5.3 当前持有者应用

独立追加提交后才尝试应用。应用事务按既有锁序读取 Task/State、关联 Operation/receipt、素材绑定，再进入 Key/quota/ledger。校验固定 runtime 与 Snapshot、attempt 归属、当前发送/应用权限、上游唯一绑定、观察格式。P0-2B 加入 fence 后，这一步必须取得新的应用许可。

CAS 失败或当前版本不支持时，只留下待恢复/阻塞进度，不回滚先前追加的证据。迟到线程本身不能把旧 claim 当作新授权；它可以唤醒恢复器，但不能越过当前 fence 写入 Task 或资金。

初始版本仍可在同一个**应用事务**中完成状态、结算、事件和 application 标记，沿用现有账务幂等。P0-2B2 再拆分状态与独立结算阶段，不能在 P0-2A 偷改已验收账务语义。

### 5.4 不伪造数据库不可用时的保证

本批能保证的是：已经成功提交的 inbox 不受后续 CAS/版本/删除失败影响。HTTP 返回后数据库完全不可写且进程立即崩溃时，纯数据库方案不能保证保存尚未提交的内存响应。此时 durable attempt/可能发送记录仍在，任务进入 unknown，不重发、不退款，走官方查询或人工核对。

增加本地加密 spool 属于单独的存储、密钥与恢复设计，不能把普通日志文件当作可靠收件箱。A1 当前只有与调用方取消分离的 10 秒保存上下文、单次追加。后续 A1.1 必须以同一 prepared 证据做有界数据库重试，失败后停止新增派发并在关库前等待在途保存；在完成前不能启用生产新写入。故障报告如实记录未持久化响应，不能把它计为“已保留证据”。

### 5.5 A1.1 保存与停机控制

以架构事实源的 A1.1 实施决定为准：同一 prepared 最多三次数据库追加、同一个 10 秒业务期限、0/200/800ms 间隔；专用主库证据连接池为 2 个连接且连接/读/写空闲超时 2 秒，不能更换数据库或重发上游。SQL 错误通过安全包装保留内部分类；身份/版本/封装错误不重试，成功提交但客户端未收到确认按同一证据幂等读回。提交的 socket 等待不由业务 context 单独保证硬上限。

最终保存失败锁存本进程发送暂停，阻止后续新增 POST/DELETE，GET/已有恢复继续；暂停可观测但不自动清除。停机先停止新后台/请求工作，再等完整在途调用（包括尚未返回的 HTTP 与脱离取消的保存）和 Recorder，45 秒总期限内未完成则非零退出。容器给 60 秒宽限；不提前主动关共享 SQL pool，不将未追踪的 relay 元数据异步工作称为已排空。本批仍默认关闭新写入，A2 兼容门禁仍独立成立。

## 6. P0-2B1：数据库时间与 fence

数据库主库决定 due、租约、续租与回收，应用 `Now()` 仅用于展示、测试数据、非授权性的本地耗时。所有涉及发送权限的比较改为主库 `UTC_TIMESTAMP(3)`，不得读取副本或使用机器时区。MySQL 当前时间函数在单条语句中取同一时间点，因此长锁等待后的许可必须在重新取得锁后再做单独、短小的条件更新；不能沿用进入事务前的时间。[MySQL 时间函数](https://dev.mysql.com/doc/refman/8.4/en/date-and-time-functions.html)

最小内部接口为：`ClaimActionTx`、`MarkMaySendTx`、`RenewLeaseTx`、`AcquireApplyPermitTx`、`ApplyReceiptTx`。返回 `{org,task,action,attempt,owner_id,fence,lease_until}` 的值对象，不能让调用方只传一个任意 task ID 就获得权限。

- `fence` 使用独立单调递增整数；Operation 行版本继续承担原有 CAS，查询 sequence 继续承担观察顺序，不能互相替代。
- 先领取 `claimed_not_sent`；再次按 owner/attempt/fence、当前契约和主库时间核验后，事务记录 `may_have_sent`，提交后才发送 HTTP。
- 在 `claimed_not_sent` 阶段进程退出，新持有者可在数据库 lease 到期后重新领取；旧线程的 `MarkMaySend` 必须失败。
- 一旦进入 `may_have_sent`，租约到期只撤销旧线程的应用权限并转核对，不自动新建有副作用的 attempt。许可提交与 HTTP 之间仍有不可消除的歧义，fence 不能令官方 HTTP 获得 exactly-once。
- 续租采用独立短事务，只允许同 owner/attempt/fence 且租约尚有效的持有者。过期 fence 不能靠续租复活；续租失败不代表上游没收到请求。
- 起始 45 秒租约、10 秒续租来自原计划，必须与实际 HTTP 超时/锁等待/调度延迟共同验收后启用。P0-2A 不先把现有 3 分钟改为 45 秒。
- HTTP 与可能阻塞的加密存储 I/O 不持有业务数据库行锁。只领取本实例可处理的数量，不把租约用作无界本地等待队列。

队列领取可以使用 `FOR UPDATE SKIP LOCKED`，但它会跳过被锁行且不是一致性账务视图。只用于任务队列选取，不用于余额、占用总数或账务核对；实施前核对生产复制模式，并用真实 MySQL 测试行锁、间隙锁、索引与 batch 行为。[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

DB 时间测试使用同一真实主库，两个 Service 的应用时钟分别偏移 ±24 小时；验证领取、续租、失效边界仍由 SQL 决定。单元测试允许注入 `LeaseClock` 接口，但 MySQL 验收必须使用生产 SQL，不可用统一 fake clock 代替。记录主库切换/时钟回拨时的结果：保守暂停新派发和续租异常告警，不能把时间跳跃解释为退款或上游槽位释放。

## 7. 查询、取消、删除及交付乱序

| 场景 | 规则 |
| --- | --- |
| 旧 query 晚于新 query 返回 | 两份证据保留；旧 sequence 不能回退新生成状态或释放新 query lease |
| 旧 query 含较早未见的有效用量，新 query 缺 usage | 观察顺序与账务证据分开；保留有效用量供固定规则核对。不能单凭 sequence 小就销毁唯一账务证据，也不能自动覆盖已结算值 |
| success 与 cancel ACK 竞态 | success/真实用量可结算；取消操作按官方最终状态核对，不因 ACK 清零 |
| DELETE 成功后 GET 404 | 资源不可查与计费结论分离；保留原账务状态/证据，不推断零费用 |
| deletion 已完成后收到 query/交付响应 | inbox 保留，公开链接不再显示；历史财务核对仍可读取，不复活软删除资源 |
| 旧 fence 收到成功创建响应 | 旧线程只追加；当前恢复者校验 scope + upstream ID 唯一绑定后推进，禁止第二次 POST |
| 同 scope 上游 ID 已属于另一任务 | 冲突证据留存，阻止自动关联和结算；不按 credential 分开绕过唯一性 |
| 未知 runtime/观察/执行格式 | 证据可追加，解释和应用等待兼容进程；不能按 current/latest 解码 |

取消/删除的所有新操作继承原任务契约与账号作用域。查询 GET 和交付补查虽没有创建副作用，也必须受同一 query gate 和作用域限制；不能为补查另开一条无限制通道。

## 8. P0-2B2：独立结算、配额和 Outbox

终态观察先持久化不等于已扣款。拆分应用阶段时，必须在一个事务中写“生成终态投影 + 独立结算待办来源 + 事件”；不能先填旧 AppliedAt，再期待扫描非终态任务找到它。

建议复用 receipt application 进度，增加独立的 generation/billing 完成标记与 due，查询 receipt 同步扩展相应字段。若需要额外结算队列表，它只存 task/固定 evidence 引用和进度，不成为第二份价格/金额事实。对同一任务的初始结算仍以既有 BillingEntry 初始键和 hold 状态机兜底；晚到冲突用量走独立的对账调整流程。

资金事务必须同时提交：UsageEvidence、BillingEntry、Ledger journal/hold、Key 和周期 quota、供应商预算敞口、State billing projection、稳定结算事件和 Outbox。任一步失败全部回滚，receipt 和结算待办仍可恢复。实际应收高于冻结的差额按现有平台吸收/调整约束记录，客户不超扣。

观察缺 usage 保留 `pending_usage`；显式零保留真实零；负值/溢出拒绝解释并保留证据。上游生成占用和财务风险敞口分别记录，不因为财务待处理永久占住已确认终态的执行槽，也不能因 Redis TTL/Worker lease 失效释放上游实际在途占用。

Outbox 发到外部消费者采用至少一次：`event_id` 稳定、消费者按该 ID 去重；发布成功后进程崩溃允许重投，不能宣称跨数据库/消息系统 exactly-once。当前项目尚未具备的外部通知渠道不在此批顺带接入。

## 9. 迁移、混跑与回退

1. P0-1 完成门禁后，冻结本批支持的运行时组合；迁移前记录旧任务/unknown/待应用回执/hold/quota/ledger 的脱敏基线。新增表与索引采用 expand migration，重复 runner 和 schema-doctor 必须通过。
2. 先部署理解 legacy 与 inbox 两类证据的兼容构建，暂不改变派发路径。真实旧构建和新构建在隔离 MySQL 中验证旧表写入、默认值、回执恢复；不能靠两个别名版本指向同一代码伪装混跑。
3. 短暂停止新派发，列出并停止所有不认识 inbox/fence 的 API 后台任务、恢复 job 与 Worker。仅靠 DB 新列或开关无法约束旧二进制；旧进程清单为空是启用门槛。
4. 确认当前在途 attempt 的归属后开启新证据路径。已可能发送的 legacy attempt 保留 legacy 恢复器，禁止盲目“重新领取”成新 attempt。旧线程可能继续返回的窗口要靠排空/进程清单和真实演练确认。
5. P0-2B1/B2 分别设置受控发布门槛；在某个新节点可续租/可独立结算时，不能让旧后台继续抢同一资源。记录最小兼容存储/恢复协议与可回退构建 digest；这不是新增可由用户填写的 runtime 版本 UI。
6. 回退先停新派发，保留兼容恢复和结算进程处理已接任务。产生 inbox-only 证据或分阶段结算后，不能退到只认识旧 Operation.ReceiptRef/QueryReceipt.AppliedAt 的构建；优先前向修复或回退到理解相同存储协议的已验收构建。
7. 数据库不做 drop/重置/恢复旧备份式回退。生产已经产生的新上游任务、证据和资金不能被旧备份抹掉；备份恢复只在隔离环境演练，真实灾难恢复单独走事故程序。

发布记录保留 source SHA、镜像 digest、migration 最大版本、支持的 runtime descriptor hash、恢复协议、实例清单、开关时间和恢复窗口。此批测试/构建使用 `laiai-release`；生产仅拉取已经验收的固定 digest。没有将本稿转成实现并通过验收前，不向生产启用新路径。

## 10. 真实 MySQL 故障矩阵

所有测试使用隔离 MySQL 8.4、合成组织/Key/额度、受控 Mock Ark。严格阻止 fallback 网络，不调用官方模型、不使用生产凭据。提供唯一 run 目录、日志摘要、运行退出码与未跳过证明；没有 `ARK_TEST_MYSQL_DSN` 的 skip 不能计为通过。

| 故障注入 | 必须断言 |
| --- | --- |
| claim 事务各写入点失败 | 无发送；Task/hold/quota 保持一致；不存在无归属 attempt |
| 取得 claim 后、MarkMaySend 前退出 | lease 到期可由新 owner 接管；旧 owner 无法取得发送许可；最多一个有副作用 HTTP |
| MarkMaySend 提交后、HTTP 前退出 | unknown，不自动再次 POST/DELETE；无退款 |
| HTTP 返回后修改 Operation.version/attempt/fence，再追加 | inbox/加密 staging/Attempt 提交，旧 claim 不改状态/账务；新恢复者处理一次 |
| 同一响应并发追加、事务提交后断线重试 | 一个相同证据 inbox 与 application；payload 不被覆盖；对账无重复 |
| 同 attempt 的冲突成功 ID/冲突用量 | 两份证据留存并核对；不自动覆盖绑定或二次扣款 |
| 状态应用事务或结算事务失败/死锁回滚 | inbox 保持；有界恢复；事件、journal、Key/周期 quota、Outbox 最终各一次 |
| 数据库在 HTTP 后不可写并终止进程 | 原 task/attempt 仍可定位为 unknown；不伪称内存响应已经落库；不重发或退款 |
| 两个 Service 主机时钟 ±24h，续租边界相等/过期 | 仅 DB 时间与匹配 owner/fence 决定权限；过期 fence 不能续租复活 |
| owner 休眠超过 lease，新 owner 接管后旧响应返回 | 旧 owner 只追加；当前 owner 应用；不重复外部副作用 |
| 新/旧 query 反序、缺用量后晚到有用量 | 状态不回退；有效账务证据不丢；原价结算或明确冲突核对 |
| cancel ACK、success、404、delete、交付刷新交错 | 生成、资源可见性、资金分别按证据处理；删除后不重新暴露链接 |
| 未知 runtime/schema 同时过期或预算不足 | 零 HTTP/零退款；未知解释优先于会导致退款的已知规则 |
| 终态已投影后重启，账务尚未提交 | 独立结算扫描仍找到它；不依赖“非终态任务”查询 |
| Outbox 发布后进程退出 | 可重投，事件 ID 不变；消费者去重；账务不重复 |
| receipt 已应用后再次恢复/未知历史任务/软删除 | 财务和已存历史保持；没有第二次 POST/无依据释放 |
| migration 二次运行、旧构建跨 expand、兼容回退 | schema 无漂移；原金额/状态/证据不被回填改写；禁止不兼容旧构建消费新路径 |

每次验收逐任务对齐：授权冻结、当前 hold、实扣、释放、已吸收差额、Key 限额、周期 quota、供应商预算、初始 journal、调整 journal、任务/回执/Outbox。金额差异容忍值为 0；不使用四舍五入后的 UI 金额掩盖差异。

## 11. 下一批实施入口

先实现 P0-2A 的一个垂直闭环：创建 HTTP 返回 → 独立 inbox 提交 → 人为令 Operation CAS 失效 → 当前恢复者消费 → queued 且只绑定一次、零重新 POST。随后覆盖取消/删除、交付补查、重复证据和删除竞态，再完成迁移与真实旧构建回退演练。

在此闭环通过前，不先扩大 Worker 数量、不先改租约参数、不用自动退款清空 unknown。P0-2A 的完成结论只限于“可归属的已提交响应不因后续 CAS 失败丢失，并可由兼容恢复者安全应用”；数据库时间、完整 fence、独立结算和 500 在途分别按后续批次验收。
