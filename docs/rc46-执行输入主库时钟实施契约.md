## 1. 建议的最小交付及不能省略的部分

建议下一批完成**现行 SQL staging 路径的执行输入生命周期闭环**：固定 schema1/schema2 的 Prepare、同事务 Stage、解密前后窗口、最后发送 SQL 的到期判断，以及 execution 用途的实际 Purge。继续使用既有 24 小时执行输入期限，不改 runtime/descriptor/hash、动作存储协议、180 秒 lease、账务规则或生产灰度开关。

不能只新增两个 reader 后宣称完成：主进程当前每分钟调用全用途 `Evidence.PurgeExpired(ctx,100)`，快钟仍可先销毁尚有效的 execution 密钥。也不能只返回普通 `ErrVideoStorage`：当前 create 把几乎所有读取失败归为 `knownUnsent`，mutation 同样会将 storage 错误记录为 NotSent；新的权威时钟失败必须有独立可判定错误，并先于这两个兜底分支返回。

首批范围推荐明确为：SQL staging 和已存对象的**执行明文读取/到期销毁**使用主库时间；主程序没有配置 Invocation BlobStore、没有运行 `UploadPending`，不在这批开放 Blob 后台上传，也不声称它的上传调度/lease 已抗主机偏移。共享 uploader 的既有 fence 和并发清理回归必须保留。若要宣称整个可选 Blob 上传生命周期抗偏移，应另列后续切片，不能把它默默算入本批。

初始时钟改造本身不需要DDL；dev1真实EXPLAIN发现扫描问题后，已批准§10的0132候选索引增量。已有 `invocation_payloads.created_at/expires_at/cleanup_after/object_deleted_at` 均为 DATETIME(3)，staging 也有毫秒时间字段；新增接口和内部准备来源标记可仅在 Go 内存中。不得回写历史时间来“校正”旧输入；`ExpiresAt` 已进入加密 AAD，CreatedAt/ExpiresAt 又进入不可变身份 HMAC。新增两枚只读派生列及索引按§10执行，不修改原时间、密文或身份字段。

## 3. 冻结 API 与域归属

以下签名已冻结。所属域均为 Invocation；不导出可由调用者自由设定的 clock，也不允许 video 直接查询 Invocation 私表。

```go

// execution 固定 capture=true/effective_request/24h；schema由方法决定。
type VideoExecutionInput struct {
    OrgID uint64
    RequestID, AttemptID string
    Body []byte
}

// schema1；复用 Create 的原业务 tx，不开启根事务，不占第二连接。
func (s *VideoStore) PrepareCreateExecutionTx(
    tx *gorm.DB, input VideoExecutionInput) (*PreparedVideoPayload, error)

// schema2；mutation 原有锁外准备。内部短主库只读事务取时，

func (s *VideoStore) PrepareActionExecution(

// 仅接受前述受控 factory 的固定 schema1/schema2 prepared 值。
// 可以在 PreparedVideoPayload 私有字段标记来源，不写数据库/不进 HMAC。
func (s *VideoStore) StageExecutionTx(
    tx *gorm.DB, prepared *PreparedVideoPayload) (string, error)
```

与 §6 兼容，已决定保留 schema1 的 `expectedSchema` 参数并只接受精确 1；schema2 只通过专用方法进入。不得把该参数改为“任何非零格式可读”，也不移除该参数改变已确定的宿主调用形状。

### 3.1 时钟和事务底座

- Invocation 自己持有固定 `UTC_TIMESTAMP(3)` helper；原业务事务使用原 ConnPool/ctx，拒绝普通 DB/DryRun/非 MySQL，NewDB 清洁链且局部 logger.Discard。不从 video 引入跨域 helper/cycle，不创建第二个所谓权威数据库。
- standalone Prepare/read 的主库来源由 `NewVideoStore` 的宿主接线保证；数据库连接不能自动证明“主库”，文档和集成测试必须核对实际注入，不能只看 Dialector 名称。
- 沿用 B1a `loc=UTC` 部署前置；本批不修改全站 DSN/session time_zone。无 replica、host-time、SQLite fallback。
- clock 查询要在相关锁/metadata 读取之后重新执行，不能使用事务开始时或候选阶段的时间。继承取消/期限，错误保持安全文本及 `errors.Is(context.Canceled/DeadlineExceeded)`；独立调用不能默默变成无界等待。
- `VideoExecutionWindow` 是一次观测，不是可缓存的发送许可、不是 fence、不能在重试中无限复用。

### 3.2 Prepare / Stage

- 两个 factory 先校验固定输入与用途规则，再读取 DB 时间，统一毫秒精度；`CreatedAt=DBTime`、`ExpiresAt=DBTime+24h`。不得允许调用者同时传入另一份 expires；保留 MaxRetention 上限校验，配置不足 24h 时明确拒绝，不静默缩短。
- 仅抽取 `Prepare` 内部加密实现的私有公共部分；原 history/delivery Prepare 行为不变。格式、correlation key、AAD、redaction/envelope、body canonicalization 与 keyring 语义完全不变。
- `StageExecutionTx` 要求真实业务事务；保留现有 savepoint、correlation 唯一与原字节幂等机制。先确认 factory/用途/schema/身份，再判断期限。metadata/staging 的插入可能等待：至少在完成相关插入/重复行当前读后，再读 DB 时间确认仍有效；到期或时钟失败回滚**本次 savepoint 全部写入**，调用方返回错误使外层 reserve/claim/EA 一并回滚。
- 不把失败准备重新生成的新密文覆盖已有 correlation 行；不修改旧 metadata 时间。Create 相同幂等请求继续在最前返回旧 Task，不能因今天 TTL/价格/时钟不可用而重新受理或重新冻结。
- 旧 `StageTx` 继续服务原 history/delivery/旧测试 API；本批所有正式 execution 写入口必须接新方法，代码搜索与调用测试证明没有遗留绕过。新 factory 的私有来源标记不能被普通 `Prepare(schema=99)` 冒充。

### 3.3 Window / reader 与错误优先级

固定顺序：主体/用途权限 → 该动作 runtime 和固定 schema → correlation/immutable identity → 当前 capture lifecycle 和 DB 窗口 → 明文读取/解密 → 最后数据库/审计阶段 → 返回。最终审计也可能等待，最后数据库阶段应先完成可能阻塞的 metadata/审计写，再读 DB 时间决定能否返回；到期或权威失败不能留下“返回明文成功”的误导审计，可回滚本短事务的成功审计，再记录拒绝结果。不能用开始读时的一次 clock 贯穿所有 I/O。任何后置失败清空已解密的缓冲区。这是最后观测保证，不可能消除最终检查后进程暂停的现实边界。

window 使用精确 metadata `FOR SHARE` 当前读：`Check*WindowTx` 复用调用者现有业务事务及 ConnPool，不在方法内部另开根事务或第二连接；锁随该调用者事务提交/回滚释放。独立 typed reader 则由自身启动短 RW 数据库阶段，结束后才做 Blob Get/AES，末段另开短 RW 事务完成当前读/审计/最后 DB 时间检查；任何 metadata 锁都不跨 Blob Get/AES/上游 HTTP。每次窗口先校验身份/格式，不能仅以 payloadID 复查时间。不得用 RR 普通快照读替代当前读，事务模式、精确锁序与验证要求见 §9.2。

新增安全错误建议为 `ErrVideoExecutionAuthorityUnavailable`，覆盖执行时钟/窗口判定的数据库失败。它可包装 ctx/driver 原因以供内部 `errors.Is`，但 `Error()` 不打印 SQL/DSN。**不能只包装成 ErrVideoStorage**；若为兼容同时可匹配 Storage，宿主必须先检查新 sentinel。

| 结果 | 宿主行为 |
| --- | --- |
| runtime/schema 未知、身份/HMAC 不一致 | 0 HTTP，不产生本地 NotSent/refund；既有未知/人工核验路径保留 |
| execution authority DB 失败/取消/超时 | 0 HTTP；准备/Stage 未提交则全回滚；已登记则保留登记/hold/receipt，让原恢复流程处理，不把故障解释为过期 |
| 支持格式且 DB 确认已过期 | 不发 HTTP。只有原 sender 的 exact claim/未发送证据和原 reducer 可处理 NotSent；单独一个 expiry 结果不授予退款权限 |
| 迟到上游证据已存在，输入已到期/销毁 | 继续 metadata-only 验证、持久化/消费；不能要求解密、延长输入期限或重发 |
| 审计失败同时发现未知格式/权威故障 | 保留优先语义，可 join 安全 sentinel；不能让 audit 错误覆盖为可触发 NotSent 的普通失败 |

旧 `ReadVideoExecutionIdentityTx` / `ReadVideoActionInputIdentityTx` 和 `ValidateVideoPayloadReferenceTx` 不改成 expiry-sensitive。`ValidateVideoExecutionSchemaTx` 仍只是 schema 门禁，不应改成退款或过期决策器。

**任何 knownUnsent / local NotSent / refund 前都必须在原事务先完成 metadata-only 固定身份验证**，包括早于 typed reader 的资产/预算失败，以及 reader/凭据准备失败。仅校验 schema 不够：`requireExecutionRuntimeTx` 当前没有验证 legacy create 的 correlation；须通过 Invocation 窄 identity reader 核对 Org、payload、用途、direction、schema、自洽 correlation，并在 video 核对固定 RequestID/AttemptID/Task/Operation 引用。已有 EA 的路径还验证其既有身份/HMAC；legacy 无 EA 不能虚构 HMAC 证明。身份或 authority 错误优先返回，不能落入普通不可读输入的 NotSent 兜底；精确 claim/runtime 原资格仍必需。

该 identity-only 检查与发送 expiry window 分离。`mutationSendIdentityTx` 同时被读取前校验和 `saveMutationNotSent` 消费，**不可直接加入 expiry 必须有效的条件**；只在真正读明文/发送资格处组合 window。支持格式、身份合法、确已到期且当前 sender 可证明未发送的输入，仍可按原 reducer 保存合法 NotSent；expiry 本身不授予释放权。已过期/已销毁输入的迟到证据恢复不增加 window。

### 3.4 最后发送边界

只在 reader 结束检查时间仍不够：clientFor、metadata 复核与最终 COUNT 可能等待。推荐由 Invocation window 返回已核对的 immutable `ExpiresAt`，在 video 现有最后 COUNT 加参数谓词 `? > UTC_TIMESTAMP(3)`，该参数只能来自本动作/本 payload 的 window。与原 exact org/task/op/version/attempt、credential/target/runtime/lease 谓词在同一条最后 SQL 中判断；video 不 JOIN Invocation 私表。

- create 的 `operationMaySend` 在原 schema/当前 Operation 核查事务中取得 window；不能在旧 legacy DELETE 上强加“原 create 输入仍可读”要求。legacy DELETE 不需要原 create 明文，schema2新动作另有自己期限。
- mutation 的 `mutationSendIdentityTx` 保持恢复身份用途与发送窗口用途清晰；只在发送资格路径补 action window。删除现有 guard 的两次 host Now TTL 比较；最后 SQL 仍按 DB time，pause 重查保留。
- window 身份必须与捕获的 payload 引用/EA HMAC/操作相符，不能从另一个较晚过期的输入取常量。
- 这不能让数据库与 HTTP 原子化，也不解决进程在最终判断后任意暂停的问题；到期/lease 失效不能触发重复 mutating 请求。fence/renewal 不在本批。

## 4. Purge、可选上传及用途隔离

保留现有 `PurgeExpired(ctx,batch)` 宿主入口，内部按**精确 purpose** 划分期限。execution 候选和重锁后到期判断使用主库时间，metadata 先当前锁定，再 clock，再清 WrappedKey/Nonce、删除 staging；cleanup_after 与 execution object_deleted_at 也来自 DB 时间。其他 purpose 的原行为保持，不能让 history 大批候选把 execution 永久挤出单个共享 LIMIT。已决定两用途各自 `LIMIT batch`，不采用可相互饥饿的单个共享 LIMIT。

两个独立 `LIMIT batch` 流（execution / 非 execution）每次最多 `2*batch` 个新销毁，cleanup 同样分别有界。必须先保持原 `1 <= batch <= 1000` 参数验证，再计算乘法；`batch=0/负值/1001/MaxInt` 均拒绝，不发生整数溢出、负 LIMIT 或无界扫描。返回值是本次实际新 capture_expired 总数，非已选择行数、非 blob deletion 数；日志/测试分开记录新销毁与 cleanup 的实际完成量，不能把失败/未命中的行算成功。主程序 batch=100，最多 200 个新销毁和另外至多 200 个 cleanup 候选；这是明确的循环上界变化，不可悄悄扩大成全表事务。每行短事务沿原 metadata→staging 方向，不能去锁 Task/Operation/钱包。

候选 SQL 对 purpose 的字符/尾空格必须精确，不能将 PAD SPACE 等值误当规范 execution；后续 Go 也复核用途。未知 schema 的 execution 不需要解密或解释即可按其已承诺期限销毁，但 metadata/attempt/receipt 必须留下，未知 schema 不因 Purge 变成“确认未发送”。未知 purpose 的既有隐私清理策略不借本批重新定义，不能被误纳入合法执行输入。

执行区 clock SQL 失败不能销毁任何该行 key/staging；独立行事务已完成的前面行按真实数量报告，不假称整批原子。blob 删除仍在事务外、沿现有私有对象引用、30 秒取消界限，失败保持可重试；不下载或保存生成媒体。grace 保持现有 2 分钟上传 lease + 30 秒 Blob timeout，不增新时长。

可选 UploadPending 存在已确认的独立协议阻断，继续保持未启用：claim 提交后、30秒 Put context 创建前的进程暂停可超过现有 grace；Purge 已销毁密钥并删除对象、记录 object_deleted_at 后，旧进程恢复并开始迟到 Put，会留下不能解密的孤儿密文。ACK fence 能拒绝状态回填，但不能保证再次删除该对象；此结论不是仅上传调度的 host clock 偏移问题。加长 grace 或再加一次 Put 前检查仍有检查后暂停窗口，不算修复。

本批 SQL staging 与执行读取/Purge 可以继续；不得为避开该问题停止 Purge、开启 uploader 或声称完整 Blob 并发生命周期已验证。保留并重验现有 Put→Purge→迟到完成的 fence/清理用例，但“Purge 完成后才启动迟到 Put”的协议修复另立任务，明确反例与未解决范围；已存对象的读取/到期销毁仍在本批边界内。

## 6. 旧二进制与发布顺序

### 6.1 格式兼容，无数据迁移

schema1=1、schema2=2；固定 RuntimeV1/ActionContract/descriptor hash、AAD、correlation、ExecutionIdentity JSON、response HMAC 均不变。新 Prepare 的“时间取自哪里”不改变 wire/storage schema；旧 binary 能解密新格式、新 binary 能解密仍有效旧格式。但旧写入的偏移时间不能推断或回填：新代码只尊重已经写入并被 AAD/HMAC 固定的 expires。

### 6.2 兼容不等于混跑安全

旧 binary 的 reader 和 Purge 都仍依 host Now。即使它理解同一个 schema，在旧 worker/旧 Purge 继续运行时也无法提供 ±24h 安全：快钟会提前毁钥，旧发送路径也可能按慢钟使用已过期明文。没有逐行 clock-version fence、共享旧进程禁行机制，增加一列也不会自动让旧 binary 停止。因此建议本批**不引入新 DDL/版本号伪装成兼容解决方案**。

发布建议：先合入可调用的 Invocation 接口与消费者/清理实现，再合入全部正式 execution producer/guard 接线；可以拆成两个可构建提交，同一 PR 或连续 PR。只有全部闭环和验收通过才声明 B1b 完成。生产切换须停止并排空所有旧执行/留存 job（保留原 10 秒证据保存及主进程 shutdown 预算），然后启动全新版本；不是长期停用新 Purge。Redis leader 只能降低同时运行概率，不能作为旧进程完全停止的证明。

回滚到 B1a 仍可恢复/读取合法旧格式，但撤销 B1b 的时钟保证；必须先 drain 新进程、确认宿主时钟正常，不能在持续注入偏移或旧 Purge 共存时宣称安全回滚。完整固定双二进制门禁要在 B1a 合入后固定真实 N-1 40SHA 与新 N 40SHA，不拿当前 dirty worktree 或替换 runtime 字符串冒充。

最小真实二进制矩阵（不复制 A2c 全 39 场景）：

1. N-1 真实 Create 写 schema1 胶囊和 pending task → N 接管一次派发/恢复；输入/账务指纹保留，不重建请求。
2. N-1 真实 schema2 Prepare/claim/register 及 durable receipt → N 在正文实际 Purge 后只消费 receipt，0 重发、一次合法状态/资金结果。
3. N 新 factory 写 schema1/schema2，N-1 正常时钟分别读取/消费；证明格式兼容，不在这项声称偏移安全。
4. 未知 schema/runtime 的已过期/已 purge 记录，两版本均不因 expiry 退款；任一已存迟到证据继续保留。

以上四场景固定 N/N-1 真实进程门禁是本批必需交付，不能用同进程新 Service、旧格式 golden 或 A2c 旧结果代替。任一场景缺失/skip 时，B1b 尚未完成部署验收。

### 9.2 window 当前读：原业务事务与短 RW 阶段分别适用

这不是“所有 window 都重新开短事务”的接口。职责固定如下：

| 调用位置 | 事务与连接 | 锁与释放边界 |
| --- | --- | --- |
| `CheckVideoExecutionWindowTx` / `CheckVideoActionExecutionWindowTx` 被业务调用 | **直接使用传入的真实原业务 tx**。不得调用 s.db 再开根事务，不得占第二连接，不得改当前事务访问模式 | 原 Task→State→Operation 之后，以 `(org_id,payload_id)` 精确 `FOR SHARE` 读 metadata，核身份/schema，再 `UTC_TIMESTAMP(3)`；锁直到原事务结束，不能宣称 helper 返回就已释放 |
| standalone typed execution reader 的前后数据库阶段 | 自己在主库启动短 **RW** 事务，`ReadOnly:false`；每阶段使用同一 ConnPool，结束后再外部 I/O | metadata `FOR SHARE` 当前读；末阶段允许写访问审计。Blob Get/AES/上游 HTTP 均在这些短事务之外，不把共享锁保持到网络完成 |
| `PrepareCreateExecutionTx` | 原 Create 幂等/预冻业务 tx；不增加根事务 | 只取 clock 与本地加密，不为了 clock 去锁 metadata；随后 `StageExecutionTx` 在原事务落 metadata/staging |
| `PrepareActionExecution` | 独立短 **READ ONLY** 主库事务可以使用，因为仅执行无表锁的 clock SELECT | 读到 DB 时间就结束事务，之后本地加密；不在这个只读阶段调用 window、Stage 或审计写入 |
| `PurgeExpired` 的 execution 单行处理 | 自己的短 RW 事务 | metadata `FOR UPDATE` → clock → metadata 密钥清理 → staging 删除；不反向锁 Task/Operation |

MySQL 官方锁定读取说明确认，`FOR SHARE` 会在等待其他事务结束后读取最新值，并持锁到本事务提交/回滚；这正是避免使用既有 RR 快照中旧 capture 状态的目的。[MySQL 8.0：Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。访问模式与当前事务隔离级别是不同概念；不能从“真实 TxCommitter”推出它是 RW。[MySQL 8.0：SET TRANSACTION](https://dev.mysql.com/doc/refman/8.0/en/set-transaction.html)。

本地实际依赖 `go-sql-driver/mysql v1.8.1` 的 `connection.go:115–130,485–506` 显示：ReadOnly=true 发 `START TRANSACTION READ ONLY`，ReadOnly=false 发 `START TRANSACTION`，**不是显式 `START TRANSACTION READ WRITE`**。所以 RW 主库连接的默认访问模式仍是宿主前置，不能把 Go bool 当成驱动已强制覆盖异常会话配置。此处不扩大为全站 DSN/SESSION 配置改造；若写审计/Stage 被只读模式拒绝，保持安全错误并停止，不重连另一个库或降级普通快照读来绕过。

本契约选择 RW reader 阶段是为了明确支撑访问审计与业务接线，**不声称所有 READ ONLY 事务执行 FOR SHARE 都必然得到1792**。`Check*WindowTx` 接口只接真实事务，不假造 GORM 中不存在的已知访问模式标志。不能将它改为遇到只读调用时偷偷开启新 RW 根事务；原业务接线和测试必须直接证明该阶段实际使用预期事务。

相应验收补强仍归 E01/E03/E06，不新增整套矩阵：

- 将池限为一个连接，原 tx 内执行 window/Stage 不得等待第二连接；同 tx 能读自己的未提交 metadata，第二连接在另一个独立测试中读不到，rollback 后消失。
- 两连接真实 RR：A 先建立旧普通快照，B 提交合法 capture 生命周期变更；A 的 window `FOR SHARE` 读取最新状态而不是旧快照。另以 B 持 metadata X 锁，证明 A 实际等待、释放后取 clock，提前/回滚都不返回过时许可。
- 记录实际锁持有者/连接及事务结束；独立 reader 在 Blob barrier 期间 metadata 不保持共享锁，Purge 可推进。最后阶段看到已过期/销毁则拒绝明文并留下准确审计。
- PrepareAction 的只读事务仅 clock 可以成功；独立只读事务对同库非临时表的真实写入拒绝作为环境正控，不把 FOR SHARE 失败硬编码为该正控。
- 新默认 reader 的真实审计成功、只读错误不绕过、ctx 取消后事务/连接归还均有行为断言；不以捕获一段 SQL 字符串代替这些证明。

### 9.3 源码冻结与验收纪律

Stage 错误清理例外：正常数据库阶段上限1秒不变；若该子ctx已取消，savepoint回滚使用同一ConnPool、`context.WithoutCancel`派生的独立最多1秒清理ctx，不增加连接或根事务。它仅完成失败写入的撤销，不重新授权Stage；回滚失败仍返回authority错误且宿主必须回滚外层业务事务。真实“staging INSERT后超时、调用者处理error再Commit”反例必须证明metadata/staging均未残留。

Purge 的返回计数以实际确认提交为准：单行 Commit 已返回成功后才发生的ctx取消不能将该行计数抹去；后续阶段可返回取消错误和已完成数量。尚未确认提交的错误不猜测成功，保留原安全失败语义。

## 13. 异常执行输入的有界待核查隔离（主控批准开发）

新增私有 `isolateInvalidCreateExecution(ctx, candidate, cause) (bool,error)`，固定原因码 `execution_identity_conflict`。只处理可重复证明的execution schema/missing/purpose/correlation/固定引用错误，不按普通字符串判断错误；ctx取消/期限、authority/DB/存储错误优先拒绝隔离。事务总期限1秒，继续原200ms主库clock；Task→State→Operation当前锁后验证已支持runtime/adapter/protocol/billing及原账务snapshot，candidate完整org/resource/kind/version/attempt/payload/runtime不变，无任何EA。未知运行时/账务版本的行不解释、不修改。

重新读取输入身份使用Invocation已有metadata-only API，但在同一事务显式FOR SHARE当前读，避免旧RR快照把已修复输入隔离；调用后与更新前均保留ctx错误，锁后取DB时间。pending仅Task仍accepted、无attempt/lease/receipt，in_flight仅精确当前claim已DB过期。满足这些条件且永久输入错误仍在时，只将Operation的status写needs_review、error_code写固定码、updated_at写DB时间；version/attempt/payload/lease/receipt、Task/State、钱包/hold/quota/预算/Key及原证据都不变。CAS丢失不假称隔离成功。

生产入口仅两处：ProcessOnce对本轮pending create的永久输入失败进行这项二次核验；recoverOperations对已过期的无EA legacy create进行核验。直接processOperation/Cancel/NotSent调用的原拒绝与零修改契约保持。每轮原候选LIMIT不扩大；隔离后不再占pending或expired候选，因此31坏行后的合法行会在有界后续周期前进，不能把简单continue视为解决饥饿。隔离发生于独立事务；原失败事务回滚后才调用，避免nested tx与部分提交。

迟到回执仍可由原持有者persistResponse按原version CAS保存，不改变该凭据、目标、版本和持久证据协议。恢复候选额外允许且仅允许本固定code的needs_review、未应用且有receipt、outcome为accepted/rejected/unknown的记录走原真实回执reducer；这不重新POST，也不以input TTL阻止已收到结果。坏身份下not_sent不能由该例外退款或循环占队列：legacy in_flight/unknown上的未应用not_sent，若claim已过期、无EA且同样永久身份错误经锁内重验，可仅隔离Operation并完整保留该回执；隔离后的not_sent不自动消费，保持人工核查。其它未知outcome不进入新增例外。有效not_sent维持原exact-once释放，schema错误不能变成无费用证明。

Worker现有OperationCounts须包含needs_review，固定操作原因仍可追溯；不得记录输入正文、密钥或SQL。最低验收覆盖：31坏输入后的同scope/跨Org合法任务多周期前进；原Task/State/资金与证据保持；pending、live/expired claim、未知运行时/账务/任意EA隔离边界；两连接当前读、修复竞态及CAS；取消/authority/数据库故障不写隔离；隔离后真实迟到accepted/rejected/unknown的保存与恢复、not_sent非法与有效正控、重复回放零重复资金。全部采用隔离MySQL/Mock，原失败库继续保留，不以清理数据替代修复。
