# LAIAI-NEXT 整体架构设计 v2

> v1 2026-06-12 起草；v2 同日修订：A1/A2 拍板落地（保留大陆市场 + 中国模型聚合；Tenant 重构为 Organization 一等公民）、新增异步 Task API 抽象（Seedance 类视频生成）、部署定址 BytePlus SG、新增"禁止移植黑名单"。
> 设计原则：把旧平台两个月的事故经验**结构性地设计进架构**，而不是作为补丁存在。

---

## 0. 定位与产品范围

**一句话**：全球化 AI 模型聚合平台（对标 OpenRouter 类产品形态），自有身份、自有网关、自有计费内核，原生支持 agent 经济（x402 按次支付 + ERC-8004 agent 信任层），内置 API Key 检测诊断工具，保留多租户白标（代理分站）商业模式。

产品能力清单：
1. **统一 API 网关**：OpenAI 兼容统一入口 + 各厂商原生透传，多上游路由/故障转移
2. **中西模型双轨聚合（核心差异化）**：西方系 + 中国系（Seedance 2.0 视频生成/Doubao/Qwen/GLM/Kimi/MiniMax）——海外开发者一站式调用中国模型是真实稀缺供给
3. **模型目录与定价**：公开模型市场页（延续 Model.vue 的定价展示逻辑，后端化），多计费单位（token/图像/视频秒）
4. **计费**：预充值（法币/加密货币）+ x402 按次微支付双模式
5. **Key 诊断工具站**：站内检测任意 API Key 的有效性/延迟/TTFT/模型清单/流式/余量 + 各厂商可用性公共状态页（获客入口）
6. **Agent 原生**：ERC-8004 AgentCard 身份 + x402 无账户按次调用
7. **Organizations/Teams**：团队工作区/共享账单/成员限额（全球 SaaS 标配）；白标为 org 付费能力（agency/区域分销商）；affiliate/referral 全球拉新（移植结算/佣金域）

## 2. 总体架构

```
                    ┌──────────────────────────────────────┐
                    │  边缘层 (Cloudflare)                   │
                    │  WAF / CDN / DDoS / 营销站(Pages/SSG)  │
                    └──────────┬───────────────────────────┘
              全球用户 ────────┤            中国大陆用户
                               │         ┌── CN 优化入口(反代, 可选CN2) ──┐
                               ▼         ▼                              │
                    ┌──────────────────────────────────────┐            │
                    │  入口网关 Caddy (移植全部 Caddyfile 经验)│◄──────────┘
                    └───┬─────────────────────┬────────────┘
                        ▼                     ▼
        ┌───────────────────────┐   ┌─────────────────────────────┐
        │ relay (数据面, Go)     │   │ core (控制面, 模块化单体, Go) │
        │ ─ OpenAI兼容统一API    │   │ ─ Identity  身份/Key/OAuth   │
        │ ─ 厂商适配器池          │   │ ─ Tenant    白标多租户        │
        │ ─ 流式 + 用量计量       │   │ ─ Catalog   模型目录/定价     │
        │ ─ hold→capture 计费    │◄──┤ ─ Ledger    复式账本(事实源)  │
        │ ─ x402 402挑战中间件    │   │ ─ Payments  7支付引擎+对账    │
        │ ─ 分布式限流(Redis)     │   │ ─ AgentTrust ERC-8004适配    │
        │   无状态,可多区域复制    │   │ ─ Diagnostics Key检测worker  │
        └───────────┬───────────┘   │ ─ Notify    邮件/飞书/webhook │
                    │               │ ─ Admin+Audit 管理/审计       │
                    │               └──────────┬──────────────────┘
                    ▼                          ▼
        ┌──────────────────────────────────────────────────┐
        │ MySQL 8.4 LTS │ Redis 7 │ CF R2(对象存储/备份)     │
        └──────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────────┐
        │ 运维 Droplet: Gitea CI / Grafana+Prom+Loki / Kuma │
        └──────────────────────────────────────────────────┘
```

**核心结构决策**：
- **控制面/数据面分离，但只有两个可部署单元**（core + relay），同一 monorepo、Go workspace。relay 是唯一需要水平扩展/多区域复制的组件，设计为完全无状态（状态全在 Redis/MySQL）。
- **模块化单体**：core 内 10 个 bounded context 以 Go package 边界隔离（internal/ 强制），模块间只走接口，禁止跨模块碰表。未来若需拆分，按 package 边界切割即可。
- **前端彻底告别注入式**：营销站 = Vue SSG 部署 CF Pages（消灭 bind-mount 部署事故类）；用户 Console + 管理后台 = 同一 Vue 3 SPA 按 RBAC 渲染，静态资源走 R2+CDN。

## 3. 技术选型（含否决清单）

| 层 | 选型 | 理由 |
|---|------|------|
| 后端 | Go 1.23+ / Gin 或 chi | 现有肌肉；relay 高并发流式场景 Go 最优 |
| 数据库 | **MySQL 8.4 LTS** | 全套运维肌肉（备份 runbook/schema-doctor/事故经验）都是 MySQL 的；solo-ops 下运维确定性 > Postgres 特性优势 |
| 迁移 | **版本化 SQL only（golang-migrate 或激活自研框架）** | GORM AutoMigrate 在新平台**永久禁用**（AlterColumn 静默损坏事故） |
| 缓存/锁/队列 | Redis 7（锁、限流、缓存）+ asynq（Redis 队列，给 Diagnostics/Notify/对账） | 不引入 NATS/Kafka 新组件 |
| 用量明细 | MySQL 按月分区表，热数据 90 天，归档至 R2 parquet | ClickHouse 推迟到日均 10w+ 请求再上 |
| 前端 | Vue 3 + Vite + TS；营销站 SSG | 沿用 web-src 肌肉，补上 TS |
| 边缘 | Cloudflare（WAF/CDN/Pages/R2） | 已有使用经验 |
| 可观测 | OTel SDK → Prometheus + Loki + Grafana（部署在运维 Droplet）+ Sentry | 旧平台无 tracing/无 Sentry 的缺口补齐 |
| CI/CD | Gitea Actions（运维 Droplet 已有 Gitea）移植 make ci/schema-doctor/release-manifest | |

**考虑过并否决**：微服务（solo-ops 运维成本爆炸）、K8s（同上）、Postgres（放弃 MySQL 运维资产）、Next.js（放弃 Vue 肌肉）、自研队列（asynq 够用）、day-1 多区域数据库（先单区域写 + 边缘缓存）。

## 4. 模块分解（core 内 10 个 bounded context）

### 4.1 Identity（全新设计，吸收薅羊毛事故）
- 自有 users 表：Argon2id 密码、TOTP 2FA、OAuth（Google/GitHub）、**email 永远必填且 canonical 化入库**（Gmail dots/+alias 标准化是写库前置，不是事后检查）——薅羊毛漏洞在 schema 层面消灭
- 注册路径：canonical email UNIQUE 约束 + Redis SETNX 并发锁（移植 v15.2 四层防御为标准件）
- API Key：`sk-laiai-` 前缀 + SHA-256 哈希存储（明文只显示一次）、per-key scope/限流/预算上限/过期时间
- Agent 身份：ERC-8004 解析的链上身份 与 x402 payer 地址 作为"轻账户"（无密码，余额由支付凭证驱动）

### 4.2 Organization（A2 拍板：Tenant 的重生，一等公民）

**判断依据**：中国式"个人代理开镜像分站赚差价"模式在欧美主流市场不成立——发现靠品牌/SEO/社区而非分销网络、支付信任壁垒高、纯加价转售无附加值且劣质分站会反噬主品牌。但底层多租户机器在全球市场有两个高价值形态，因此**重构而非砍掉**：

**统一抽象**：`Organization` 是账户体系的唯一容器——
- 个人账户 = 单成员 org（默认隐式创建）
- 团队 = 多成员 org：**全球 SaaS 标配能力**（OpenAI/Anthropic/OpenRouter 均有）——共享余额与账单、成员角色（owner/admin/member/billing）、per-member API Key 与限额、用量按成员归集。这是海外 B2B 增长的 must-have，复用的正是旧平台多租户的全部机器
- 白标 = org 的**付费能力开关**（`white_label` entitlement）：自定义域名（Caddy on-demand TLS + 域名校验 API 移植）、品牌/主题、加价率、独立结算——目标客户是 agency 与区域分销商（东南亚/中东/拉美等支付与语言本地化有真实价值的市场），是高阶套餐而非核心 GTM
- 个人拉新 = **affiliate/referral 计划**（全球通用）：旧平台佣金树、H-5 事务、72h catchup、结算逻辑代码级移植，只是剥掉"开分站"这层皮

一个抽象消灭旧平台 user/tenant 双体系并行的根因性复杂度——这就是 A2 要求的"深度优化"。
移植项：三级缓存域名解析（本地→Redis→MySQL + 熔断）、租户隔离红线（org_id 谓词 repository 层强制）；修复项：org 设置读取加 Redis 缓存 + 显式失效。

### 4.3 Catalog（Model.vue 逻辑后端化）
- 模型注册表：厂商/模型/能力标签（chat/vision/video/image/audio/embedding）/上下文长度/官方价
- **多计费单位（v2 扩展）**：tokens（input/output/cache 分列）、图像张数、**视频秒×分辨率档位**（Seedance Fast/Standard/Pro 三档）、请求次数——Catalog 定价行 = (model, unit, tier) 三元组，ledger 侧统一折 USD
- 定价引擎：官方价 × 平台倍率 × org 加价 → 实价；BASE_RATE 公式后端统一计算，前端只展示
- 公开 API `/v1/models` + 营销站模型市场页数据源

### 4.4 Relay（数据面，全新自研——新平台的心脏）

**能力底线承诺（KEY 聚合转换全量保留）**：NewAPI 的核心价值——不同类型上游 KEY 的聚合与协议转换——逐项映射：渠道 Key 池（不同厂商 Key 类型统一管理，信封加密）、协议双向转换（统一格式↔各家原生）、多 Key 轮询/权重/故障转移（**增强**：健康分由 Diagnostics 探针实时喂养）、模型映射、计费截流（**增强**：hold→capture）、重试降级（**增强**：覆盖异步任务类 + per-channel 并发闸）。
**工程量诚实评估**：Relay 是重建中最大单体工程。NewAPI 的真实护城河是多年积攒的厂商边角案例（流式 usage 抽取差异 / function calling 格式 / 错误码语义 / 超时行为），对冲三件套：① 工作区 `new-api-src/` 作为 adapter 字段映射与边角案例的**参考规范**（知识移植，非代码移植）；② 上线只做头部 6-8 家 adapter（覆盖 95%+ 真实流量），长尾按需增补；③ 每个 adapter 强制真实 raw response fixture 测试（epay 字段方言教训的泛化）。

- 协议：对外 OpenAI 兼容 `/v1/chat/completions` 等 + `/native/{provider}/...` 原生透传
- 适配器池（A1 拍板：中西双轨是核心差异化）：
  - 西方系：OpenAI / Anthropic / Gemini / Groq / Mistral / xAI ...
  - 中国系：**BytePlus ModelArk（Seedance/Doubao 国际版，同云内网接入）**、DashScope intl（Qwen，新加坡端点）、Zhipu GLM、Moonshot Kimi、MiniMax、SiliconFlow ...
  - 统一 Usage 抽取接口（流式 SSE 末帧 usage / 非流式 body / token 估算兜底三档）
- **Adapter 边角案例清单（来自 NewAPI v1.0.0-rc.1~rc.10 情报挖矿，每条都是上游真实修过的 bug，进 fixture 测试）**：
  - 跨格式 tool-call 转换（OpenAI↔Claude↔Gemini），**含并发 tool calls**（rc.10）
  - reasoning 字段透传不丢（空 reasoning 字段曾被丢弃，rc.1）——o 系/推理模型必测
  - 图像编辑 multipart 的参考图与 metadata 保留（rc.4）、image quality 参数透传（rc.10）
  - 大媒体流式管道化而非内存缓冲（rc.10 修的是内存占用过大）——视频/图片产物走 io.Pipe 直通 R2
  - 超大上游错误体截断后入日志（rc.10）；auto-disabled 渠道严格退出调度池（rc.10）
  - **upstream_request_id 全量采集**（rc.6 上游为此加列加索引）：每次调用记录厂商侧 request-id（OpenAI x-request-id / Anthropic request-id 等），与我们 trace_id 关联——找厂商开工单的唯一凭证，schema 出厂即有此列
- **异步 Task API 抽象（v2 新增——视频/图像生成类模型的硬需求）**：Seedance 类模型是"提交任务→轮询/回调→取产物"模式，与 chat 流式完全不同。Relay 增加统一任务编排层：
  - 对外统一接口：`POST /v1/tasks`（或兼容各家 video/images generations 风格端点）→ task_id → `GET /v1/tasks/{id}` 轮询 + 用户 webhook 回调
  - 任务状态机：queued → running → succeeded/failed/cancelled，上游侧轮询/回调适配按 adapter 实现
  - 产物管线：上游产物（视频/图片）拉取 → R2 存储 → 签名 URL 下发（产物保留期可配，计入存储成本）
  - 计费：任务类按 hold（预估上限）→ capture（按实际秒数/分辨率档位）——与 chat 共用 ledger 三原语，无特殊路径
  - 上游并发约束管理：per-channel 并发闸（如 Seedance 公测 2 QPS/3 并发）进调度器，超限排队而非打爆上游
- **Provider-proximity 出口路由**：relay 节点带区域标签，调度时按"上游就近"选择出口节点（中国系模型走 SG 节点出口最优）
- **计费时序 = hold → capture**：请求前按 max_tokens 估算冻结，响应后按真实 usage 结算释放差额。**结构性消灭 TrustQuota 类问题**（旧 NewAPI 预检设计导致低余额 burst 403）
- 路由：渠道权重 + 健康分（由 Diagnostics 探针喂）+ 故障转移 + 黏性（同会话同渠道）
- 限流：Redis Lua 原子计数为唯一事实（旧平台"Redis 挂了退化单机 local map"的多实例缺陷不再保留；Redis 不可用 = relay 降级拒绝而非放飞）
- x402 中间件挂在此层（见 5.2）

### 4.5 Ledger（资金事实源——全平台地基）
- **复式账本升格为唯一事实源**：余额是 journal 的物化视图，不是独立可写的列
- journal 表：append-only，`(idempotency_key UNIQUE)` 强制每笔资金动作幂等；DECIMAL(20,8)（USDC 6 位小数天然覆盖）
- 账户类型：user_credit / user_commission / tenant_margin / platform_revenue / hold（冻结户）
- 三原语：`hold(amount)` → `capture(hold_id, actual)` → `release(hold_id)`；充值/提现/结算/转账全部走 journal
- 内部单位：**USD 单币种**（USD-first 迁移经验直接定为出厂设定），展示层做多币种换算（移植 FX 模块 + 每日锁汇率）
- 漂移自检 job：每日 journal 重放 vs 物化余额对账（旧 shadow ledger Phase 2 设想成为标配）

### 4.6 Payments（移植精华 + 新增 x402）
- 引擎注册表原样移植，7 引擎：Stripe / EPay / PayPal / Crypto / Webhook / Custom / **x402**
- **引擎契约升级（epay 方言事故的结构性消解）**：每个引擎必须实现 `CreateOrder + HandleCallback + QueryOrder` 三件套，QueryOrder 缺失 = 不准上线；单元测试 fixture 强制使用真实 raw response
- 对账 job 一级公民：5 分钟主动 Query 对账（移植全部 10 条安全红线 + 13 个 Prometheus 指标模式）
- callback 状态机移植教训：入金事务接受 `pending | expired` 双状态（uid=967 事故），终态 failed/refund 只 ACK 不翻转
- 渠道凭证 AES-GCM 信封加密（见 5.5 密钥分层）
- **订阅制计费（上游情报验证的市场需求，NewAPI rc.8/rc.10 连续两轮加码订阅）**：第三种计费模式（预充值 / x402 按次 / **订阅套餐**）——订阅 = 周期性 ledger grant（按月授予额度 + 到期回收），entitlement 挂在 Organization 上，与 Stripe Billing 订阅对象对接；CN 侧月卡套餐同模型。排期 M3+，但 ledger 的 grant/expire 原语 M0 就要预留

### 4.7 AgentTrust（ERC-8004 适配层——刻意做薄）
- 平台侧：注册平台 agent 身份于 Identity Registry，serve `/.well-known/agent-card`（能力/定价/x402 支付方式声明）
- 调用方侧：可选解析 caller 的 8004 身份 → 关联轻账户 → 信誉加权（如更高初始限额）
- 信誉回写：服务完成后写 Reputation Registry 的适配器
- **全部锁在 `AgentTrust` 接口后**：标准年轻（2025 出生），规范变动只换适配器，core 其他模块零感知

### 4.8 Diagnostics（Key 检测工具站——安全敏感组件）
- 产品面：用户提交任意厂商 Key → 检测有效性/延迟/TTFT/可用模型/流式支持/余量额度；平台自有渠道的持续探针 → 公共状态页（SEO 获客入口）
- 架构：asynq 队列 + 独立 worker 池；**出站强制走 egress 代理 + 厂商域名白名单**（SSRF 防御）；被测 Key 信封加密落盘、TTL 自动清除、**全链路日志禁止出现 Key**（脱敏中间件强制）
- 探针结果回流 Relay 路由健康分（一鱼两吃）

### 4.9 Notify（旧平台缺失的统一通知层）
- 邮件（验证码/账单）、飞书告警（移植 Uptime Kuma 关键词经验）、租户 webhook

## 5. 横切设计

### 5.1 资金不变量（红线继承）
旧平台 RED LINES 升格为新平台平台级不变量，写入 CI 检查与 code review checklist：
1. 资金动作必须在 DB 事务内 + journal 同写
2. 幂等键强制（UNIQUE 约束兜底，不依赖应用层判断）
3. 余额永不直接 UPDATE（只能由 journal 派生）
4. 入金接受 pending|expired，终态只 ACK
5. 每个支付引擎必须可主动 Query 对账
6. 租户数据强隔离（每查询 tenant_id 谓词，repository 层强制）

### 5.2 x402 两档落地
- **第一档（上线即有）**：x402 作为充值通道——Payments 第 7 引擎，USDC(Base) 入金 → facilitator verify/settle → journal 入账。复用对账模式做链上确认兜底。
- **第二档（差异化，M4）**：Relay 原生按次支付——无 Key 请求返回 `402 + 报价`，client 带 `X-PAYMENT` 重试，facilitator 验证后放行，settle 异步 + journal 记账；payer 地址聚合为轻账户支持余额预存减少链上交互。
- 两档共用同一 ledger 原语，无特殊路径。

### 5.3 多租户白标
- 域名接入三步保留（CNAME + 域名表 + TLS on-demand），Caddy 经验全移植（handle 包裹 respond、trusted_proxies 显式声明——两个 trap 写入 Caddyfile 模板注释）
- 租户定价 = Catalog 加价层；结算 = 移植 settlement/commission 域逻辑（H-5 事务、72h catchup、UNIQUE 幂等）

### 5.4 可观测性（补齐旧平台全部缺口）
- OTel trace 全链路（含后台 job——旧平台 trace 只覆盖 auth 路由）
- 结构化日志 + **PII/Key 脱敏层**（旧平台无脱敏）；操作日志不含 payload——调用数据查询走 Invocation Store（§6.1，30 天留存）
- 移植 13 个业务指标模式，新增 relay 黄金指标（TTFT/上游错误率/hold-capture 偏差）
- Sentry 接入（panic 带 stack——旧平台 recover 不打栈）

### 5.5 安全设计
- **密钥分层（KYC 轮换陷阱的结构性消解）**：所有信封加密密文头部带 `key_id`，轮换 = 新增 key + 双 key 解密单 key 加密，彻底消灭"必须按顺序轮换否则 PII 不可读"这类陷阱
- 秘密管理：.env 0600 纪律移植 + 备份 GPG 加密 + 轮换流程文档化（Secret hygiene 审计经验）
- 构建确定性：所有产物禁止嵌时间戳（CI gate 检查），镜像按 digest pin 部署（compose fallback 回滚事故的结构性消解：**部署只认 digest，release-manifest 校验为部署流水线强制关卡**）

## 6. 数据架构

- MySQL 单实例起步（8.4 LTS），库内按模块前缀分 schema 命名空间；半年内上一从库（读分离 + 备份源）
- Redis 用途白名单：分布式锁 / 限流计数 / 会话与 token / 租户域名缓存 / asynq 队列——**禁止业务事实存 Redis**（缓存丢失必须无损）
- R2：备份（移植双层备份 runbook）/ 用量归档 / 前端静态资源 / KYC 附件 / Invocation Store 数据体
- 数据生命周期：用量明细 90 天热 + R2 归档；audit 永久；journal 永久；**Invocation Store 30 天滚动**

### 6.1 Invocation Store——调用数据留存层（30 天可查询，对标 AWS 调用日志模式）

**准则修订（2026-06-12 用户拍板）**：原"payload 永不落库"改为**分层留存**——操作日志依然绝对干净，但增设一个专门的调用数据留存层，完整保存请求/响应数据 30 天供查询（对标 AWS Bedrock invocation logging / CloudTrail 的模式：专门的地方、有限的时间、受控的访问）。

- **存什么**：完整请求/响应 payload（prompt/completion/任务参数与产物引用）+ 调用元数据（org/key 指纹/模型/渠道/usage/延迟/upstream_request_id/trace_id）
- **怎么写**：relay 热路径**异步投递**（asynq 队列，绝不阻塞转发；队列积压时丢 payload 保元数据，宁缺不卡）
- **怎么存**：元数据进 MySQL 按日分区索引表（可按 org/key/模型/时间/状态查询）；payload 体信封加密（密文头带 key_id）写 R2，索引行持对象指针——查询走索引、取详情拉 R2 解密
- **怎么删**：30 天滚动——分区表 DROP PARTITION + R2 lifecycle rule 双层自动过期，删除不依赖应用代码正确性
- **谁能看**：org 成员只能查本 org（org_id 谓词强制）；平台侧 payload 解密 root-only；**每次 payload 解密读取写 audit_events**（移植旧平台"root-only PII 解密 + 审计"纪律）
- **per-org 可关**：org 可选 zero-retention（仅保元数据不存 payload）——海外企业客户的合规刚需，也是销售卖点
- **红线边界重申**：API Key 明文/密码/支付凭证**任何层都永不落库**（Key 只存 SHA-256 指纹）；Invocation Store 是 payload 的唯一合法落库点，操作日志（stdout/Loki）仍然全链路禁止 payload 与 PII
- 排期：M2（与 relay 同期落地，调用日志从第一天就有）

## 7. 基础设施与部署拓扑（A6 拍板：BytePlus SG 为主 + 多云分散）

**BytePlus 评估结论**：
- ✅ 选它的核心理由：**ModelArk 同云内网 = Seedance 2.0/Doubao 的官方国际通道最优接入**（2026-06 核实：Seedance 2.0 自 04-14 在 ModelArk 国际公测，实名认证即开 API）；字节骨干网对中国大陆及亚太连通性好；SG/Johor 区域可用；ECS 跑 Compose-on-VM 架构无障碍
- ⚠️ 风险与对冲：生态/管控面成熟度不及 AWS/GCP（我们不依赖云厂商托管服务，影响小）；字节系地缘政治敏感度（对冲：架构云中立，Compose+CF 边缘使整体搬迁成本 ≈ 一次 rsync + DNS 切换；备份/CI/监控全部放在 BytePlus 之外）
- 结论：**接受 BytePlus 为主节点云，但刻意保持"可一周内全量撤离"的姿态**——这不是不信任，是 solo-ops 的风控纪律

**起步拓扑（3 节点 + 边缘）**：
| 节点 | 位置/云 | 角色 | 规格建议 |
|------|---------|------|---------|
| node-core | **BytePlus SG (ECS)** | core + MySQL + Redis + Caddy | NVMe 8C16G（scale ladder 经验直接上 NVMe） |
| node-relay-1 | **BytePlus SG (ECS)** | relay + Caddy；中国系模型出口（ModelArk 内网/就近）+ 全球上游 | 4C8G |
| ops-droplet | **DO（现有，跨云）** | Gitea CI / Grafana+Prom+Loki / Kuma / 备份编排 | 现有复用 |
| 边缘 | **Cloudflare** | WAF/CDN/Pages（营销站）/R2（备份+产物+静态资源） | — |

- **全球低延迟靠 CF 边缘而非多云**；增长后第二 relay 节点选 US 西（西方系上游就近），即形成中西双出口
- **CN 大陆入口**：延续现行 CN2 双入口反代经验（注意：大陆侧持牌云是火山引擎而非 BytePlus，大陆 PoP 不假设 BytePlus 提供；现有 CN2 链路供应商关系直接复用）
- **跨云容灾纪律**：备份双层（本地 + CF R2 WNAM，移植 runbook）、CI/监控/告警全在 DO 侧——BytePlus 全 region 故障时，监控告警与恢复能力完整存活
- 扩展路径：relay 横向加节点（US 西 → 欧）→ core 读写分离 → 用量明细迁 ClickHouse → （远期）控制面多活
- 部署：Docker Compose per node（镜像 digest pin）+ Gitea Actions：`make ci`（vet/test/build/前端构建/确定性检查）→ schema-doctor diff gate → release-manifest 落盘 → 镜像拉取发布（消灭 bind-mount rm -rf 类事故：前端不再 bind mount，走镜像或 R2）
