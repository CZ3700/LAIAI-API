# LAIAI-NEXT 整体架构设计 v2

> v1 2026-06-12 起草；v2 同日修订：A1/A2 拍板落地（保留大陆市场 + 中国模型聚合；Tenant 重构为 Organization 一等公民）、新增异步 Task API 抽象（Seedance 类视频生成）、部署定址 BytePlus SG、新增"禁止移植黑名单"。
> 设计原则：把旧平台两个月的事故经验**结构性地设计进架构**，而不是作为补丁存在。

---

## 0. 定位与产品范围

**一句话**：全球化 AI 模型聚合平台（对标 OpenRouter 类产品形态），自有身份、自有网关、自有计费内核，原生支持 agent 经济（x402 按次支付 + ERC-8004 agent 信任层），内置 API Key 检测诊断工具，保留多租户白标（代理分站）商业模式。

产品能力清单：
1. **统一 API 网关**：OpenAI 兼容统一入口 + 各厂商原生透传，多上游路由/故障转移
2. **中西模型双轨聚合（核心差异化）**：西方系 + 中国系（Seedance 2.0 视频生成/Doubao/Qwen/GLM/Kimi/MiniMax）——海外开发者一站式调用中国模型是真实稀缺供给
3. **模型目录与定价**：公开模型市场页（延续 Model.vue 的定价展示逻辑，后端化），多计费单位（token/图像/视频秒）
4. **计费**：预充值（法币/加密货币）+ x402 按次微支付双模式
5. **Key 诊断工具站**：站内检测任意 API Key 的有效性/延迟/TTFT/模型清单/流式/余量 + 各厂商可用性公共状态页（获客入口）
6. **Agent 原生**：ERC-8004 AgentCard 身份 + x402 无账户按次调用
7. **Organizations/Teams**：团队工作区/共享账单/成员限额（全球 SaaS 标配）；白标为 org 付费能力（agency/区域分销商）；affiliate/referral 全球拉新（移植结算/佣金域）

## 2. 总体架构

```
                    ┌──────────────────────────────────────┐
                    │  边缘层 (Cloudflare)                   │
                    │  WAF / CDN / DDoS / 营销站(Pages/SSG)  │
                    └──────────┬───────────────────────────┘
              全球用户 ────────┤            中国大陆用户
                               │         ┌── CN 优化入口(反代, 可选CN2) ──┐
                               ▼         ▼                              │
                    ┌──────────────────────────────────────┐            │
                    │  入口网关 Caddy (移植全部 Caddyfile 经验)│◄──────────┘
                    └───┬─────────────────────┬────────────┘
                        ▼                     ▼
        ┌───────────────────────┐   ┌─────────────────────────────┐
        │ relay (数据面, Go)     │   │ core (控制面, 模块化单体, Go) │
        │ ─ OpenAI兼容统一API    │   │ ─ Identity  身份/Key/OAuth   │
        │ ─ 厂商适配器池          │   │ ─ Tenant    白标多租户        │
        │ ─ 流式 + 用量计量       │   │ ─ Catalog   模型目录/定价     │
        │ ─ hold→capture 计费    │◄──┤ ─ Ledger    复式账本(事实源)  │
        │ ─ x402 402挑战中间件    │   │ ─ Payments  7支付引擎+对账    │
        │ ─ 分布式限流(Redis)     │   │ ─ AgentTrust ERC-8004适配    │
        │   无状态,可多区域复制    │   │ ─ Diagnostics Key检测worker  │
        └───────────┬───────────┘   │ ─ Notify    邮件/飞书/webhook │
                    │               │ ─ Admin+Audit 管理/审计       │
                    │               └──────────┬──────────────────┘
                    ▼                          ▼
        ┌──────────────────────────────────────────────────┐
        │ MySQL 8.4 LTS │ Redis 7 │ CF R2(对象存储/备份)     │
        └──────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────────┐
        │ 运维 Droplet: Gitea CI / Grafana+Prom+Loki / Kuma │
        └──────────────────────────────────────────────────┘
```

**核心结构决策**：
- **控制面/数据面分离，但只有两个可部署单元**（core + relay），同一 monorepo、Go workspace。relay 是唯一需要水平扩展/多区域复制的组件，设计为完全无状态（状态全在 Redis/MySQL）。**现状注记（2026-07）**：网关暂驻 core 进程（relay/ 为占位壳）；三处进程内状态待多副本前收敛——①渠道健康分 EWMA（重启置满分、副本间不共享，可接受各自为政的保守起点）②未配 Redis 时模型级限流退化进程内窗口（多副本必须配 Redis）③credential polling 原子计数（副本各自轮询，均匀性略降无正确性问题）。
- **模块化单体**：core 内 10 个 bounded context 以 Go package 边界隔离（internal/ 强制），模块间只走接口，禁止跨模块碰表。未来若需拆分，按 package 边界切割即可。
- **前端彻底告别注入式**：营销站 = Vue SSG 部署 CF Pages（消灭 bind-mount 部署事故类）；用户 Console + 管理后台 = 同一 Vue 3 SPA 按 RBAC 渲染，静态资源走 R2+CDN。

## 3. 技术选型（含否决清单）

| 层 | 选型 | 理由 |
|---|------|------|
| 后端 | Go 1.23+ / Gin 或 chi | 现有肌肉；relay 高并发流式场景 Go 最优 |
| 数据库 | **MySQL 8.4 LTS** | 全套运维肌肉（备份 runbook/schema-doctor/事故经验）都是 MySQL 的；solo-ops 下运维确定性 > Postgres 特性优势 |
| 迁移 | **版本化 SQL only（golang-migrate 或激活自研框架）** | GORM AutoMigrate 在新平台**永久禁用**（AlterColumn 静默损坏事故） |
| 缓存/锁/队列 | Redis 7（锁、限流、缓存）；~~asynq~~（2026-07 对齐：至今未引入——对账/清扫/模型同步走 leader 租约定时循环 + DB 幂等，已够用；引队列的时机 = Diagnostics/Notify 统一层落地时再评估） | 不引入 NATS/Kafka 新组件 |
| 用量明细 | MySQL 按月分区表，热数据 90 天，归档至 R2 parquet | ClickHouse 推迟到日均 10w+ 请求再上 |
| 前端 | Vue 3 + Vite + TS；营销站 SSG | 沿用 web-src 肌肉，补上 TS |
| 边缘 | Cloudflare（WAF/CDN/Pages/R2） | 已有使用经验 |
| 可观测 | OTel SDK → Prometheus + Loki + Grafana（部署在运维 Droplet）+ Sentry | 旧平台无 tracing/无 Sentry 的缺口补齐 |
| CI/CD | ~~Gitea Actions~~ → **GitHub Actions**（2026-07 对齐：.github/workflows/ci.yml = make ci + web + redline 三 job）；schema-doctor 在 make ci（migrate-lint）+ migrate-smoke；release-manifest 为部署前后手动纪律（进流水线待正式机） | |

**考虑过并否决**：微服务（solo-ops 运维成本爆炸）、K8s（同上）、Postgres（放弃 MySQL 运维资产）、Next.js（放弃 Vue 肌肉）、自研队列（asynq 够用）、day-1 多区域数据库（先单区域写 + 边缘缓存）。

## 4. 模块分解（core 内 10 个 bounded context）

### 4.1 Identity（全新设计，吸收薅羊毛事故）
- 自有 users 表：Argon2id 密码、TOTP 2FA、OAuth（Google/GitHub）、**email 永远必填且 canonical 化入库**（Gmail dots/+alias 标准化是写库前置，不是事后检查）——薅羊毛漏洞在 schema 层面消灭
- 注册路径：canonical email UNIQUE 约束兜底（2026-07 对齐：Redis SETNX 并发锁未引入——DB UNIQUE 已是并发安全的唯一事实，重复注册撞约束即失败，无需第二层锁）
- API Key：`sk-laiai-` 前缀 + SHA-256 哈希存储（明文只显示一次）、per-key scope/限流/预算上限/过期时间
- Agent 身份：ERC-8004 解析的链上身份 与 x402 payer 地址 作为"轻账户"（无密码，余额由支付凭证驱动）

### 4.2 Organization（A2 拍板：Tenant 的重生，一等公民）

**判断依据**：中国式"个人代理开镜像分站赚差价"模式在欧美主流市场不成立——发现靠品牌/SEO/社区而非分销网络、支付信任壁垒高、纯加价转售无附加值且劣质分站会反噬主品牌。但底层多租户机器在全球市场有两个高价值形态，因此**重构而非砍掉**：

**统一抽象**：`Organization` 是账户体系的唯一容器——
- 个人账户 = 单成员 org（默认隐式创建）
- 团队 = 多成员 org：**全球 SaaS 标配能力**（OpenAI/Anthropic/OpenRouter 均有）——共享余额与账单、成员角色（owner/admin/member/billing）、per-member API Key 与限额、用量按成员归集。这是海外 B2B 增长的 must-have，复用的正是旧平台多租户的全部机器
- 白标 = org 的**付费能力开关**（`white_label` entitlement）：自定义域名（Caddy on-demand TLS + 域名校验 API 移植）、品牌/主题、加价率、独立结算——目标客户是 agency 与区域分销商（东南亚/中东/拉美等支付与语言本地化有真实价值的市场），是高阶套餐而非核心 GTM
- 个人拉新 = **邀请码注册赠额**（2026-07 拍板收窄）：仅保留 aff_code 邀请码 + 被邀请人注册赠额（invite_grant_usd）；**返佣分成整域移除**——佣金树/H-5 事务/72h catchup/结算逻辑不移植（原"affiliate 返佣计划"设想作废，避免分成税务与对账复杂度）

一个抽象消灭旧平台 user/tenant 双体系并行的根因性复杂度——这就是 A2 要求的"深度优化"。
移植项：三级缓存域名解析（本地→Redis→MySQL + 熔断）、租户隔离红线（org_id 谓词 repository 层强制）；修复项：org 设置读取加 Redis 缓存 + 显式失效。

### 4.3 Catalog（Model.vue 逻辑后端化）
- 模型注册表：厂商/模型/能力标签（chat/vision/video/image/audio/embedding）/上下文长度/官方价
- **多计费单位（v2 扩展；2026-07 记录实现演进）**：tokens（input/cached/output 分列）、图像张数、TTS 字符、STT 按次、Realtime 音频 token、视频（时长×分辨率）——**实现为 model_prices 扁平多列（九类价）+ 两层分组倍率**，而非原设想的 (model, unit, tier) 三元组行式定价；视频分辨率/时长档位系数在各 task adaptor 代码内（真机标定值），**改档价需发版**=已知取舍。ledger 侧统一折 USD 不变。若运营高频调档价成为痛点，再引入行式定价
- 定价引擎：官方价 × 平台倍率 × org 加价 → 实价；BASE_RATE 公式后端统一计算，前端只展示
- 公开 API `/v1/models` + 营销站模型市场页数据源

### 4.4 Relay（数据面，全新自研——新平台的心脏）

> **内核规范依据**：`docs/newapi-kernel-knowledge.md`（NewAPI 1022 文件五路精读提炼）。§7 是 LAIAI-NEXT 内核差距清单，按 P0/P1/P2 排期。每实现一项补对应 fixture 测试。

**能力底线承诺（KEY 聚合转换全量保留）**：NewAPI 的核心价值——不同类型上游 KEY 的聚合与协议转换——逐项映射：渠道 Key 池（不同厂商 Key 类型统一管理，信封加密）、协议双向转换（统一格式↔各家原生）、多 Key 轮询/权重/故障转移（**增强**：健康分由 Diagnostics 探针实时喂养）、模型映射、计费截流（**增强**：hold→capture）、重试降级（**增强**：覆盖异步任务类 + per-channel 并发闸）。
**工程量诚实评估**：Relay 是重建中最大单体工程。NewAPI 的真实护城河是多年积攒的厂商边角案例（流式 usage 抽取差异 / function calling 格式 / 错误码语义 / 超时行为），对冲三件套：① 工作区 `new-api-src/` 作为 adapter 字段映射与边角案例的**参考规范**（知识移植，非代码移植）；② 上线只做头部 6-8 家 adapter（覆盖 95%+ 真实流量），长尾按需增补；③ 每个 adapter 强制真实 raw response fixture 测试（epay 字段方言教训的泛化）。

- 协议：对外 OpenAI 兼容 `/v1/chat/completions` 等 + `/native/{provider}/...` 原生透传
- **OpenAI Responses API 双向互通（2026-07-04 定设计，商用迭代指令 §3.2；追平 New API rc.16 核心能力）**：
  - **入站 `/v1/responses`**（Responses 客户端 → 任意 chat 上游）：复用 Anthropic 入站的成熟架构——ingress 把 Responses 请求转 OpenAI canonical 替换 body，复用**完全不改动**的 HandleChatCompletions（auth/admission/定价/hold/重试/capture 全套），egress 用同步转换 ResponseWriter 把 chat 输出实时转回 Responses 形态（非流式 JSON / 流式事件序列 response.created→output_item.added→output_text.delta→…→response.completed）。资金安全性质同 Anthropic 入站：计费只认上游 usage，转换 bug 只影响展示、绝不影响扣费。
  - **无状态边界**（2026-07 对齐实现）：`previous_response_id` 明确拒绝（400）；`store` 字段**忽略（软降级）**——store 不影响计费与转发语义，而 OpenAI SDK 常默认携带该字段，硬拒会误伤标准客户端；本平台不做 Responses 会话存储不变。built-in tools（web_search 等托管工具）上游不支持时拒绝，不静默降级。
  - **出站 openai-responses adapter**（chat 客户端 → Responses-only 上游，如 Codex 系模型）：新 adapter 家族（profile.Adapter="openai-responses"），buildRequest 做 chat→Responses 请求转换，pipeJSON/pipeSSE 做 Responses→chat 响应/流转换；渠道级选择（运营把 Responses-only 上游的渠道标为该家族即完成"自动选择转换链"）。
  - usage 映射纪律：input_tokens⇄prompt_tokens、output_tokens⇄completion_tokens、input_tokens_details.cached_tokens⇄prompt_tokens_details.cached_tokens；usage 缺失沿用 BUG-H2 的按字段独立兜底估算，绝不少收。
  - fixture 纪律不变：request/response/stream/error 四类 fixture 全覆盖（文本/stream/tool call/多模态/reasoning/错误帧/usage 缺失）。
- **渠道级 Header/Param Override（2026-07-04 定设计，商用迭代指令 §3.4）**：运营不写代码接入"有方言的上游"。
  - `channels.param_override`（JSON，0033）：进 adapter **前**对请求体深合并——值为 `null` 删除该字段（嵌套亦然，如 `{"stream_options":{"include_obfuscation":null}}`），对象递归合并，其余覆盖。应用在**每次 attempt 的副本**上（不同渠道不同 override，绝不跨渠道残留）。
  - **资金钳制保护**：`model/stream/max_tokens/max_completion_tokens/n/thinking/messages` 为受保护键——写入时 admin API 拒绝、应用时防御性跳过。否则 override 抬高输出上限会绕过 hold 估算钳制（P0-2 同类负余额风险）。
  - `channels.header_override`（JSON，0033）：在 adapter 默认头**之后**应用（运营优先级最高）；值 `null` 删除头；支持 `{{credential}}` 占位符注入渠道解密凭证——自定义认证头（X-Api-Key 等）不需要把上游 key 明文写进配置（红线 7 兼容）。`Host`/`Content-Length` 禁改（破坏 HTTP 语义）。
  - 审计：override 变更写 audit log 时只记 **keys 列表**不记值。调用日志不逐条记 override keys（偏离指令原文，理由：channel_id + 渠道审计历史可完整重建当次 override 状态，逐条冗余 30 天且无查询价值）。

    - **统计底座（A3）**：进程内 (model×channel) 聚合缓存（`chanStats`，60s TTL 惰性刷新）——单条 SQL 拉近 1h invocations（`channel_id>0`，上限 2 万行采样）在内存算每 (model,channel) 的 calls/成功率/p50/p95/avg_frt。零迁移、零热路径查询；多副本各自聚合（与健康分 EWMA 同哲学——本地视角足够好）。同一聚合逻辑以 24h 窗口服务 admin「model×channel 交叉看板」（`GET /api/admin/model-channel-stats`，现算不缓存，运营低频）。
    - **策略求解（A2）**：每请求 `X-LAIAI-Route` 头 > key 级默认（`api_keys.route_policy`，0043）> 平台默认 `order`。枚举 `order|latency|throughput|price`；未知值**静默回落 order**（宽容向后兼容，请求详情面板可见实际生效值）。
    - **策略语义**：`order`（默认）= 现状层内 (weight+smoothing)×健康分 加权随机，行为逐字不变；`latency` = 层内按 p50 升序确定性取最优（样本 <10 的渠道视为无数据排最后、组内退回加权随机——冷渠道不因无数据被饿死也不被误优先）；`throughput` = 层内按成功率降序、p50 升序 tie-break（同上无数据处置）；`price` = **当前单一平台定价下渠道无差价，等价 order**（枚举保留：BYOK/渠道差价出现时接真数据，文档先行承诺不虚假差异化）。
    - **与 failover 的关系（A4）**：策略只改「层内第一选择」；失败仍走既有 exclude 换渠道 + attempt 跨层降级——确定性排序下 exclude 自然使次优接棒，降级链免费获得。
    - **作用域（第一期）**：chat 主链路 + forwardWithFailover 六模态（embeddings/rerank/images/edits/audio）；task/realtime 沿 order（提交/建连是低频动作，策略收益小，后续按需）。
    - **fail-open**：统计缓存刷新失败/无数据 → 回落 order；策略路径绝不引入新的请求失败模式。
  - **请求级 provider preference（2026-07-11 定设计；顶级审计修排名 6，对标 OpenRouter `provider` 对象）**：客户端可按请求钉/避上游厂商。
    - **请求形态**：body 顶层 `provider: {order?: [..], only?: [..], ignore?: [..], allow_fallbacks?: bool}`（OpenRouter 兼容命名），转发上游前**剥除**（上游不认识该字段）。匹配键 = 渠道 `provider`（adapter 家族名，大小写不敏感）——渠道名是运营内部信息不外露，厂商家族是客户端可知的公开语义。
    - **语义**：`only`/`ignore` 是候选集过滤（作用于全部 priority 层与 BYOK 虚拟层之上，与 BYOK 隔离谓词/ServesModel 同级）；`order` 是层内确定性重排（列表内按序优先、未列出的排后；与 X-LAIAI-Route 策略的关系 = **过滤先于策略**，策略在过滤后的候选集内选择）。`allow_fallbacks:false` = 过滤后无候选/全失败即失败，绝不越出名单（默认 true 时 only/ignore 仍硬过滤——OpenRouter 的 fallbacks 指模型链，此处指"是否允许在名单外兜底"，v1 语义＝名单恒硬过滤，`allow_fallbacks` 仅保留解析不改行为，避免"名单是建议"的歧义）。
    - **作用域**：chat 主链路 v1（OpenRouter 的 provider 对象同样只在 chat 语义下定义；六模态 typed 请求结构不载该对象，留 v2 按需）。**红线交互**：过滤纯选路决策不碰 ledger；过滤后无渠道 = 与"模型无渠道"同一失败面，不引入新错误形态。
  - **模型级 fallback 链（2026-07-11 定设计；顶级审计修排名 7，对标 OpenRouter `models:[a,b,c]`）**：主模型全渠道失败自动降级到备选模型。
    - **请求形态**：body 顶层 `models: ["a","b","c"]`（OpenRouter 兼容）；`model` 存在时为主模型、models 为备选序列；链长钳 3（与 attempt 预算同哲学）。转发上游前剥除 `models`。
    - **资金语义（红线）**：**每个模型一份独立 hold**——切换模型前先 release 当前 hold + 退 key quota 预留，再按新模型价新建 hold（幂等键 `relay:<request_id>#<模型序号>`，杜绝跨模型共用 hold 结算错价）。结算/Invocation 记实际成功的模型；响应 usage/model 即真实所用模型（客户端可见降级结果，不静默冒充主模型）。
    - **降级条件**：仅"该模型此路不通"类失败进入下一模型——无可用渠道、上游重试预算耗尽、hold 余额不足（备选可能更便宜）、key quota 不足（同理）；**客户端 400 类（请求本身不合法）绝不换模型**（换了也一样错，且掩盖真错误）。已开始向客户端写响应（流式首字节已出）后绝不换模型。
    - **作用域**：chat 主链路 v1（六模态/task 无此语义需求）；与 provider preference/策略选路正交叠加（每个模型各自走完整选路）。
    - **数据模型**：复用 channels 表 + `owner_org_id`（0044，0=平台渠道）——adapter/信封加密/映射/override/failover 全套机器免费获得。**绝不建第二套渠道体系**。
    - **隔离红线（等级同 org_id 谓词）**：选路过滤谓词 `owner_org_id = 0 OR owner_org_id = 请求方 org`，在 tierForAttempt 分层骨架内结构性强制——BYOK 渠道对其他 org **不存在**。org 自有渠道构成**虚拟最高优先层**（先用自己的 key，失败经既有 exclude/attempt 降级回落平台渠道并按平台价计费——fallback 语义文档化，OpenRouter 同）。
    - **作用域（v1）**：chat 主链路 + forwardWithFailover 六模态；task/realtime 不参与（picker 调用传 orgID=0，只平台渠道）。
    - **计费**：BYOK 命中时结算 = 正常计价 × `byok_fee_percent`（ext_settings，默认 5%，0 合法=纯免费路由）。hold 仍按全价预扣（渠道命中在 hold 之后才知道），结算释放差额——用户需有全价余额头寸（费用条款文档化）。费率乘点在各 settle 的 actual 计算处（quota 侧自然一致）；capture≤hold 不变量保持（费率<1）。
    - **安全**：① base_url 用户可控 = SSRF 面——创建期 `ValidateAdvancedUpstreamURL`（**强制 https、绝不 allow-private**，严于 advanced_custom）+ 转发期 guarded client（clientFor 对 owner_org_id>0 渠道恒走拨号复检）；② provider 白名单 = 已知云端档案（openai/anthropic/gemini/groq/mistral/xai/deepseek/moonshot/zhipu/dashscope-intl/minimax/siliconflow），排除 advanced_custom/自建家族/TaskOnly；③ key 信封加密同渠道纪律，列表只回显 SHA-256 指纹前 12；④ 每 org 上限 10 条；⑤ 增删启停写审计（actor=user，绝不记明文）。
    - **计价前提**：BYOK 模型必须在 model_prices 已定价（费率是平台价的百分比）——未定价模型照常拒绝，BYOK 不是"接入任意模型"的后门（那是 admin 渠道的职责）。
    - **对抗 review 通过（2026-07-10）**：跨 org 白嫖/费率错配/capture>hold/少收/SSRF/隔离泄漏六条逐一结构性挡住（tierForAttempt 谓词 + byokFactor 命中渠道一致性 + [0,100] 费率钳制 + guardedClient 恒守卫）。硬化 1 项：guardedClient 补跨主机重定向剥认证头（与 NewGuardedClient 对齐，防 BYOK 上游恶意 302 泄漏 org 自己的 key）。**已知次优（非红线，不修）**：同 org 多 BYOK 渠道在一个虚拟顶层，attempt 0 选中其一失败被 exclude 后 attempt 1 直接落平台层，第二个 BYOK 不重试——后果是按平台全价计费（多收用户、平台不亏，方向安全）；改需动 attempt→tier 重试预算语义，有回归风险，留待有真实多-BYOK 用户反馈再做。
- 限流（**2026-07 对齐实现 + 记录偏离决策**）：模型级限流 Redis **已接线**（配 `LAIAI_REDIS_ADDR` 时 INCR+EXPIRE 跨实例一致；未配时进程内窗口，单实例正确）。**有意偏离原"Redis 不可用=降级拒绝"**：实现为 fail-open 放行——理由是"限流是保护、不是收费闸"（收费闸是 hold/quota，Redis 故障不影响资金安全；拒绝全部流量的代价高于短暂放行）；auth 端点限流 Redis 不可用时退化本地令牌桶（拒绝全部登录代价更高）。该偏离经 2026-07 差距清查复核接受，黑名单 #2 以本条为准。
  - 模型级限流：每 (org, model) 固定 60s 窗口计数，开关+RPM 走 ext_settings（5s 缓存）；chat/images/embeddings 入口在 keyGate 后强制，超限回 429+Retry-After。视频任务走自己的 per-channel 并发闸，不重复限流。
- x402 中间件挂在此层（见 5.2）

### 4.5 Ledger（资金事实源——全平台地基）
- **复式账本升格为唯一事实源**：余额是 journal 的物化视图，不是独立可写的列
- journal 表：append-only，`(idempotency_key UNIQUE)` 强制每笔资金动作幂等；DECIMAL(20,8)（USDC 6 位小数天然覆盖）
- 账户类型：user_credit / user_commission / tenant_margin / platform_revenue / hold（冻结户）
- 三原语：`hold(amount)` → `capture(hold_id, actual)` → `release(hold_id)`；充值/提现/结算/转账全部走 journal
- 内部单位：**USD 单币种**（USD-first 迁移经验直接定为出厂设定），展示层做多币种换算（移植 FX 模块 + 每日锁汇率）
- 漂移自检 job：每日 journal 重放 vs 物化余额对账（旧 shadow ledger Phase 2 设想成为标配）

### 4.6 Payments（移植精华 + 新增 x402）
- 引擎注册表原样移植，7 引擎：Stripe / EPay / PayPal / Crypto / Webhook / Custom / **x402**
- **引擎契约升级（epay 方言事故的结构性消解）**：每个引擎必须实现 `CreateOrder + HandleCallback + QueryOrder` 三件套，QueryOrder 缺失 = 不准上线；单元测试 fixture 强制使用真实 raw response
- 对账 job 一级公民：5 分钟主动 Query 对账（移植全部 10 条安全红线 + 13 个 Prometheus 指标模式）
  - **已落地（M4，2026-06-14）**：`Engine.QueryOrder` 进契约（epay 按 out_trade_no 查、方言用 `status`；stripe 按 session id 查 payment_status，session id 经 `0022` 落 `topup_orders.provider_ref`）；`Server.ReconcileTopups` 扫 pending+超 minAge 单 → Query → 经**与 callback 同一资金路径** `creditPaidOrder`（幂等键 topup:order）入账；main.go 每 5min ticker，minAge 2min。Prometheus 指标待补。
- callback 状态机移植教训：入金事务接受 `pending | expired` 双状态（uid=967 事故），终态 failed/refund 只 ACK 不翻转
- 渠道凭证 AES-GCM 信封加密（见 5.5 密钥分层）
- ~~订阅制计费~~ **（2026-07 拍板变更：不做订阅）**：全站采用预充值余额 + 按量计费单一模式（x402 按次为第二模式）；无订阅表、无套餐页。原设计（周期性 ledger grant + entitlement + Stripe Billing）保留于此仅作历史参考——若未来重启，ledger 的 grant/expire 原语已具备

### 4.7 AgentTrust（ERC-8004 适配层——刻意做薄）
- 平台侧：注册平台 agent 身份于 Identity Registry，serve `/.well-known/agent-card`（能力/定价/x402 支付方式声明）

### 4.8 Diagnostics（Key 检测工具站——安全敏感组件）
- 产品面：用户提交任意厂商 Key → 检测有效性/延迟/TTFT/可用模型/流式支持/余量额度；平台自有渠道的持续探针 → 公共状态页（SEO 获客入口）
- 架构：asynq 队列 + 独立 worker 池；**出站强制走 egress 代理 + 厂商域名白名单**（SSRF 防御）；被测 Key 信封加密落盘、TTL 自动清除、**全链路日志禁止出现 Key**（脱敏中间件强制）
- 探针结果回流 Relay 路由健康分（一鱼两吃）

**v1 落地（2026-07-10，批次 7）——同步无落盘 Key 检测**：三处对原设计的**有意偏离，均更安全或更省**：
- **同步而非 asynq 队列**：Key 检测是快速有界操作（单次 GET /models，超时封顶）。同步执行 → 被测 Key **全程只在内存、绝不落库**，直接消灭设计里"信封加密落盘 + TTL 清除"的整个攻击面（红线 7 的最强形态：零持久化 = 零泄漏面）。这是对原异步设计的**严格安全增强**，也与本项目 no-asynq 现实一致。
- **SSRF = 拨号守卫 + provider 白名单**（复用 relay/probe.go 的 `fetchModels`）：恒经 `guardedClient(false)` 拨号复检解析后 IP（DNS-rebinding-safe，metadata 恒拦），**绝不放行私网**（不吃 `advanced_custom_allow_private` 开关，与 BYOK 同纪律，防租户探测平台内网）；provider 走白名单（已知云端家族），custom base_url 强制 https + `ValidateAdvancedUpstreamURL(false)`。比"静态域名白名单"更强（后者防不住 DNS rebinding）。
- **红线 7 全链路**：handler 绝不 log 请求体/key；`fetchModels` 错误路径本就只返 "unreachable"/"HTTP %d"（不回显 key）；响应绝不含被测 key。检测报告 = 有效性 + 延迟 + 模型数/样例 + 网关线索。
- **v1 认证 + per-IP 限流**（`authRateLimit`）：outbound HTTP 的滥用面（拿平台当扫描器/SSRF 跳板/撞库）由登录门 + 限流挡住。**公开获客变体**（免登录，SEO 入口）需验证码 + 更严限流，记为后续。
- **本期不做**（记 deferred）：TTFT/流式/余量额度（各需真实推理调用花用户 key 的钱 + 各家 quota 端点方言）、探针结果回流健康分（健康分已由真实流量 EWMA 喂养，一鱼两吃是增量）、平台自有渠道持续探针（公共状态页已由真实流量近 1h 成功率派生，§5.4）。
- **对抗安全审查（2026-07-10，3 维 6 发现）**：红线 7（key 泄漏）维度**零确认**——gemini `?key=` 的 url.Error 泄漏被 fetchModels 的通用错误（"unreachable"/"HTTP %d" 不含 key）封死。3 条 confirmed 同根因（诊断=鉴权后的公网探测/滥用 oracle），已按比例硬化：① **端口 443-only**（custom base_url 非标端口 400，灭任意端口扫描）；② **状态回显折叠**（diagFailResult 去逐字 HTTP 状态码，只留 invalid_key/forbidden/unreachable/error 粗粒度语义类，灭精确状态 oracle）+ Gateway banner 仅 provider 默认端点时回显（custom base_url 置空，灭 Server/Via 侦察面）；③ **per-user 配额**（diagLimiter 以 userID 为键，突发 20 后 2/min，抗 IP 轮换的账号侧封顶，挡"用平台出口 IP 洗白撞库"）。1 条驳回（ByokAllowPrivateForTest foot-gun——无生产写点 + metadata 恒拦，不可利用）。内网/metadata 方向确被拨号守卫挡住（测试覆盖 private/metadata→400）。
- **v1.1 admin 丰富指纹（2026-07-10，批次 8）——运维检测上游渠道质量**：用户澄清主用途 = 运维给自己要上货的中转/渠道 key **验真+溯源**，非公开获客工具。**使用者=可信平台管理员 → 上面 3 条 confirmed 的"公网侦察 oracle"顾虑对本档不成立**（无"攻击者借道"），故 admin 档该给的全给：
  - **端点真实 IP + 反向 DNS（PTR）**：httptrace GotConn 抓 TCP 对端 IP + LookupAddr 取 PTR（best-effort 短超时）——PTR 常暴露 `*.openai.com`（官方）或某 VPS（中转站）。
  - **鉴权字段 + key 平台指纹**：Bearer/x-api-key/?key= 由协议族定；key 平台由**前缀模式表**推断（sk-ant-→anthropic、AIza→google、gsk_→groq…）。**红线 7**：只输出推断平台 + 匹配到的公开前缀常量（全平台同款，非本 key 密文），**绝不 slice 用户 key 的任何随机段**。
  - **全套签名响应头**：Server/Via/CF-Ray/openai-organization/openai-version/anthropic-ratelimit-*/x-ratelimit-* 等——展示真实限额/网关/组织线索（响应头不含请求 Authorization，红线 7 安全）。
  - **官方验真（启发式，非密码学）**：PTR 命中平台域 或 响应带平台签名头（+CF-Ray 是官方常态非中转）→ official_direct/official_via_cdn；前缀说是 X 但响应无 X 签名头 + PTR 不匹配 + Server 通用（nginx/openresty）→ relay_suspected。**诚实声明**：API Key 是不透明凭证、无可验证签名，"验真"永远是启发式置信判断，不是密码学证明。
  - **中转判断 + 手数**：Via 头能数出的手数（多数中转会剥 Via → 手数 -1 不可知）；指纹错配（前缀平台 vs 实际端点特征）→ likely_relayed；无信号 → inconclusive。**诚实声明**："经过几手"只在 Via 未被剥时准确。
  - **不可知项（物理限制，明确不做）**：key 的**发行源服务器**——key 不带发行源信息，无法反推。
  - 门控：`POST /api/admin/diagnostics/check`（adminRequired）；拨号守卫随运营 allow-private 开关（与 adminProbeChannel 同口径，operator 合法内网上游可探）。普通用户 `/api/diagnostics/check` 维持硬化极简档不变。
  - **对抗审查（8 发现，红线 7 维度零确认）**：4 条指纹正确性 confirmed 全修（都直击"给假官方结论"的核心失效）：① **PTR 匹配缺标签边界**（裸 HasSuffix 把 api.**my**openai.com 仿冒域判官方）→ ptrHasDomainSuffix 要求 `.suf` 边界 + 大小写归一；② **透传签名头被判 direct**（透明反代 nginx 透传官方响应头无 Via）→ direct 只认 **FCrDNS 正向确认的 peer 身份**（PTR 名正解回指 peerIP 才可信，攻击者可控 PTR 即便设成 api.openai.com 也过不了正解回指），转发头降级为 official_via_cdn/inconclusive；③ **Via 短路误杀官方**（Google Front End 恒发 `Via: 1.1 google`）→ viaOfficialTokens 白名单剔官方 token，只数第三方手数；④ Via 手数空段/尾逗号过计 → TrimSpace 跳空段。红线 7 兜底 redactHeadersContaining（响应头值含 key 即丢，防 echo 端点反射）——2 条 key 泄漏发现经复核为假阳性（key 只回提交者本人、不落库/日志）。

### 6.1 Invocation Store——调用数据留存层（30 天可查询，对标 AWS 调用日志模式）

> **实现现状（2026-07-04 对齐，商用迭代指令 P1-1 路线 A）**：当前实现是 **metadata-only**——
> 只存调用元数据（org/user/key id、request_id、模型、渠道、状态、tokens、费用、延迟、client
> IP/UA/Referer），`payload_object_key` 恒为空；写入是进程内 channel 批量 INSERT（非 asynq，
> 队列满丢弃的是**整条元数据**并计数告警——与目标架构"丢 payload 保元数据"不同，路线 B 落地时修正）；
> 30 天过期靠应用层批量 DELETE（非 DROP PARTITION）。下方 payload 信封加密入 R2 + root-only
> 解密 + 解密审计 + per-org zero-retention 是**目标架构（路线 B，未排期）**，产品文案与 UI
> 不得在落地前承诺 payload 可查。红线边界（最后一条）不受影响，现在与将来都成立。
>
> **模态标（2026-07-07，migration 0040）**：元数据增 `modality` 列（chat/embeddings/rerank/image/
> audio_speech/audio_transcription/realtime/video/music），各数据面 handler 在构造 Invocation 时打标，
> 供请求日志按模态过滤（`/api/usage?modality=`，图像日志页数据源）。历史行 modality=''，不回填
> （按 model 反推不可靠，宁缺勿错）；值集是对外 API 契约，只增不改。

**准则修订（2026-06-12 用户拍板）**：原"payload 永不落库"改为**分层留存**——操作日志依然绝对干净，但增设一个专门的调用数据留存层，完整保存请求/响应数据 30 天供查询（对标 AWS Bedrock invocation logging / CloudTrail 的模式：专门的地方、有限的时间、受控的访问）。

- **存什么**：完整请求/响应 payload（prompt/completion/任务参数与产物引用）+ 调用元数据（org/key 指纹/模型/渠道/usage/延迟/upstream_request_id/trace_id）
- **怎么写**：relay 热路径**异步投递**（asynq 队列，绝不阻塞转发；队列积压时丢 payload 保元数据，宁缺不卡）
- **怎么存**：元数据进 MySQL 按日分区索引表（可按 org/key/模型/时间/状态查询）；payload 体信封加密（密文头带 key_id）写 R2，索引行持对象指针——查询走索引、取详情拉 R2 解密
- **怎么删**：30 天滚动——分区表 DROP PARTITION + R2 lifecycle rule 双层自动过期，删除不依赖应用代码正确性
- **谁能看**：org 成员只能查本 org（org_id 谓词强制）；平台侧 payload 解密 root-only；**每次 payload 解密读取写 audit_events**（移植旧平台"root-only PII 解密 + 审计"纪律）
- **per-org 可关**：org 可选 zero-retention（仅保元数据不存 payload）——海外企业客户的合规刚需，也是销售卖点
- **红线边界重申**：API Key 明文/密码/支付凭证**任何层都永不落库**（Key 只存 SHA-256 指纹）；Invocation Store 是 payload 的唯一合法落库点，操作日志（stdout/Loki）仍然全链路禁止 payload 与 PII
- 排期：M2（与 relay 同期落地，调用日志从第一天就有）

## 7. 基础设施与部署拓扑（A6 拍板：BytePlus SG 为主 + 多云分散）

**BytePlus 评估结论**：
- ✅ 选它的核心理由：**ModelArk 同云内网 = Seedance 2.0/Doubao 的官方国际通道最优接入**（2026-06 核实：Seedance 2.0 自 04-14 在 ModelArk 国际公测，实名认证即开 API）；字节骨干网对中国大陆及亚太连通性好；SG/Johor 区域可用；ECS 跑 Compose-on-VM 架构无障碍
- ⚠️ 风险与对冲：生态/管控面成熟度不及 AWS/GCP（我们不依赖云厂商托管服务，影响小）；字节系地缘政治敏感度（对冲：架构云中立，Compose+CF 边缘使整体搬迁成本 ≈ 一次 rsync + DNS 切换；备份/CI/监控全部放在 BytePlus 之外）
- 结论：**接受 BytePlus 为主节点云，但刻意保持"可一周内全量撤离"的姿态**——这不是不信任，是 solo-ops 的风控纪律

| 边缘 | **Cloudflare** | WAF/CDN/Pages（营销站）/R2（备份+产物+静态资源） | — |

- **全球低延迟靠 CF 边缘而非多云**；增长后第二 relay 节点选 US 西（西方系上游就近），即形成中西双出口
- **CN 大陆入口**：延续现行 CN2 双入口反代经验（注意：大陆侧持牌云是火山引擎而非 BytePlus，大陆 PoP 不假设 BytePlus 提供；现有 CN2 链路供应商关系直接复用）
- **跨云容灾纪律**：备份双层（本地 + CF R2 WNAM，移植 runbook）、CI/监控/告警全在 DO 侧——BytePlus 全 region 故障时，监控告警与恢复能力完整存活
- 扩展路径：relay 横向加节点（US 西 → 欧）→ core 读写分离 → 用量明细迁 ClickHouse → （远期）控制面多活
- 部署：Docker Compose per node（镜像 digest pin）+ Gitea Actions：`make ci`（vet/test/build/前端构建/确定性检查）→ schema-doctor diff gate → release-manifest 落盘 → 镜像拉取发布（消灭 bind-mount rm -rf 类事故：前端不再 bind mount，走镜像或 R2）

## 10. 上线策略（v2.3 重写：干净冷启动，无任何迁移）

本项目与旧平台零关系——无用户迁移、无余额导入、无支付切换、无域名切换。上线是标准的新产品发布：

1. **内部验证**（M1-M2）：新服务器部署，团队自用 + 授信测试账户打真实流量
