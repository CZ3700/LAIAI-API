## 隔离与备份

- 使用线上同版本 MySQL，`--single-transaction` 一致性导出，经压缩后直接加密保存；分别验证解密退出码、压缩完整性和备份完成哨兵。
- 恢复目标为独立临时容器，无网络、无端口映射、不挂载生产数据卷、不启动 core/worker。数据库位于临时内存文件系统，容器内存上限 512 MiB、CPU 0.5、swap 上限 0，并检查内核实际限额。
- 短暂校验数据放在专用、不可交换的 ramfs；错误诊断加密留存。原始备份、数据摘要、业务差异详情和加密口令均留在服务器受限位置，不进入 Git 或开发数据库。
- 演练持续监测线上健康和宿主资源；退出时移除临时容器、卸载诊断内存目录，并核对 Docker 卷清单未变化。
- 初次容器门禁因 Docker cgroup v2 的 `OomKillDisable` 空字段停止；核验[官方行为](https://docs.docker.com/engine/containers/runmetrics/)后改查 cgroup v2 的真实内存/swap 限额。未把空字段默认为已验证限额。

## 既有数据门禁

本轮发现已有账户余额与 journal 汇总存在最小金额单位级差异。旧、新 `CheckDrift` 的口径一致，差异不是升级产生，也不能作为允许忽略的浮点噪声。保留受限报告和原数据，需要核查成因并按账务流程裁定；本轮没有直接更新余额、补造 journal 或清理冻结。

另外，旧、新渠道删除路径均只删除父渠道，凭据表没有级联删除，可能留下子凭据。本轮观察到此类既有记录，将其作为保留基线并待分类核查，不能单凭孤儿记录断言恢复损坏，也不自动删除历史凭据。

因此区分两个结论：**隔离迁移兼容性**与**上线数据就绪性**。继续在副本上的诊断不会豁免原有数据门禁；不得将“迁移无数据变化”解释为“历史账务已正确”或 `RELEASE_PASS`。

最终演练结论为 `COMPATIBILITY_PASS_RELEASE_BLOCKED`。前置严格检查明确停止后，使用显式兼容诊断模式继续验证副本，无修改既有账务的步骤。回填的首轮校验查询曾因新旧列排序规则不同报 1267；只将校验查询的文本比较改为精确字节比较，随后完整重跑通过，没有调整正式表结构或数据来迎合测试。

最终演练采样：临时实例内存峰值约 305 MiB，宿主可用内存最低约 558 MiB、磁盘最低约 2.35 GiB。退出后临时实例与诊断 ramfs 均为 0，Docker 卷清单一致，线上 core 仍 healthy、健康接口仍为 200，迁移序列仍为 0048。这些数值是本轮小型数据库样本的结果，不是其他部署的数据量或时长保证。
