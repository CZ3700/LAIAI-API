## 2. 已核实的故障路径

### 2.1 QueryReceipt 最老 40 条占窗

`worker.go:recoveryQueryCandidates` 当前只选择支持合同、未应用且 `apply_error_code != settlement_conflict` 的回执；`recoverQueryReceipts` 按 `received_at,attempt_id LIMIT 40` 读取。`applyQueryReceipt` 在 Task→State→receipt 锁内对 ObservationJSON 进行 json.Unmarshal；语法或目标字段类型错误使应用事务回滚。后续诊断事务写 `query_apply_failed` 和既有 State.sync_state=needs_review，不写 AppliedAt。下一轮仍选相同 40 条。逐条错误仅 Warn，函数最后返回 nil。

这条路径已经静态确定；本草案没有声称已执行新的 MySQL 复现实验。格式未知的 runtime/schema 已在 LIMIT 前过滤，它们不是此坏队列夹具的替代品。

### 2.2 不能仅抽编排而保留吞错

## 3. 最小数据方案：已选复用 ApplyErrorCode，只加 due/version

两列路线已获主控批准；下表保留选择依据，迁移编号0133，仅此独立树实施，具体MySQL行为尚待真实验收。

| 方案 | 字段 | 实际价值 / 并发反例 | 结论 |
| --- | --- | --- | --- |
| A | 现有 ApplyErrorCode + 新 recovery_due_at + recovery_version | due 非空是可调度时间，NULL 是人工隔离屏障；version 阻止旧失败处理覆盖后来成功或另一轮已经写入的进度 | 已选 |
| B | 新 mode、reason、due、version 共四列 | mode/reason 可独立于旧诊断代码，但会复制现有 AppliedAt/ApplyErrorCode；还须证明三者组合。N−1 仍不认识 mode，四列也不能让旧程序遵守隔离 | 本片不选，缺少必须新增两列的业务反例 |

两列不可省的具体例子：

- **due**：只有固定永久错误码可排除语法坏记录，但死锁、锁超时、事件写失败等可恢复故障仍会占最老窗口。不能把 received_at 改成重试时间，它是原证据到达时间；也不能把临时故障永久隔离。due 提供 DB 时间退避，并使复发故障让出窗口。
- **version**：A、B 均读取 v 后应用失败；B 已先在当前锁内决定退避或永久隔离并提交 v+1，A 的迟到诊断不得再把 B 的 NULL 改回 due，或把 B 的 due 向后推移。这里不依赖尚未交付的人工解除：两者都未应用，单看 AppliedAt 无法分辨较新的进度。失败进度写须同时匹配当次锁内捕获的 version；锁内当前身份重新核验仍然不可省。版本到 uint64 上限时失败且不写，不允许回绕。
- **mode 不必新增**：AppliedAt 非空=应用完成；AppliedAt 空且 due 非空=等待调度；AppliedAt 空且 due NULL=隔离。这个屏障不依赖旧诊断写是否改变 ApplyErrorCode。
- **reason 不必新增**：使用现有固定 ApplyErrorCode。N−1 可能把新永久码覆为 query_apply_failed，但它不更新新 due，不能清掉 NULL 屏障。混跑期间诊断码可能不稳定需如实承认；这不足以为本片增加另一套状态。不可因此把新的 reason 表当成旧程序的 fence。

建议物理形状：

```
recovery_due_at  DATETIME(3) NULL DEFAULT (UTC_TIMESTAMP(3))
recovery_version BIGINT UNSIGNED NOT NULL DEFAULT 0
```

NULL 绝不是“立即重试”或“回退默认”；新代码不得 COALESCE(NULL, NOW())。receipt 原始身份、ObservationJSON、PayloadRef、ReceivedAt 等保持不变。新 producer 省略 due 时由 DB 生成 UTC 默认；新 ORM 的实际 INSERT 必须证明省略字段而非显式写 NULL，不能仅依赖 GORM 标签猜测。原版 writer 省略两列也得到同样默认。需要修改/测试唯一生产 QueryReceipt 写入口；既有手写 fixture 按相同字段契约更新，不能偷偷加入 host-clock 回退。

[MySQL 8.4 默认值规则](https://dev.mysql.com/doc/refman/8.4/en/data-type-defaults.html) 允许括号表达式与内置函数；具体 UTC_TIMESTAMP(3) DDL、ALTER 对历史行的填充值及本项目 ORM 行为仍必须真实 MySQL 验收。不能用 CURRENT_TIMESTAMP 代替：它取 session 时区，Go DSN 的 loc=UTC 本身不是 MySQL time_zone 设置。[时间函数规则](https://dev.mysql.com/doc/refman/8.4/en/date-and-time-functions.html)

## 4. 候选索引、历史兼容与迁移

建议保留全部旧索引，新增：

```
(runtime_version, adapter_version, protocol_contract_version,
 observation_schema_version, applied_at, recovery_due_at,
 received_at, attempt_id)
```

候选在 LIMIT 前同时要求原支持合同/账务快照/非 create quarantine、AppliedAt IS NULL、recovery_due_at IS NOT NULL 且 <= UTC_TIMESTAMP(3)，原 settlement_conflict 排除仍保留。排序改为 due、received_at、attempt_id；最大仍 40。日期范围不使用 host Now。不要在索引列上施加 CAST/COALESCE，也不使用 FORCE INDEX。

历史 settlement_conflict 原本就不自动应用。若仅增加默认 due，它们会留在可扫描时间范围并被后置错误码条件排除。建议迁移中只对**精确原固定码**且 recovery_version=0 的这些旧行，将新 due 置 NULL；不动原列、金额或证据。这是新列回填，不是退款或重新分类未知 ObservationJSON。该回填必须单列验收和部署成本，不能把“大表 UPDATE”隐藏在 expand-only 字样里。新 N 产生 settlement_conflict 时同事务设置 NULL；N−1 仍可能留下非 NULL 的旧码，所以统一高效保证以旧 worker 完整 drain 为前提。

0133包含单条原子ALTER与只写新列的幂等回填两步；最终合入前仍核对编号无冲突。中断点分别验证 ALTER 后未记版本、回填后未记版本，重复 Up 不更改已经 version>0 的进度。旧 writer INSERT/UPDATE 旧列、真实 Reserve/结算、全部旧列投影/唯一键必须保持。Schema doctor 通过不证明 default 表达式和新索引正确，需 information_schema/SHOW CREATE/真实旧 SQL 正控。

真实 EXPLAIN 使用生产 candidate SQL/Vars，覆盖：大量已应用历史、大量 due=NULL review、未来 due、未知 runtime/schema 和极少合格行；实际记录 key/access/rows/filter/排序，不以小库 PASS 或“索引存在”代替扩展性证据。固定支持合同必须在 LIMIT 前；无合法结果时须在 SQL deadline 内返回，不承诺无限大历史表必然常数时间。

## 5. 锁内分类与进度写入

### 5.1 身份与顺序

保持现 `LockBillingTaskTx` 的 Task→State 锁和原账务合同核验，然后锁精确 `(org_id,task_id,attempt_id)` QueryReceipt。所有恢复、失败标记、复核/解除都采用同一顺序，不反转为 receipt→Task。事务为主库 RW；current FOR UPDATE 读，不用旧 RR 快照判断。

应用前先检查已 AppliedAt、受支持完整 runtime/receipt schema、精确 Org/Task/Attempt/sequence 与固定 Task/State 归属；未知格式保持拒绝，不改为永久 JSON 错。现 tombstone/stale-sequence 短路顺序与原 reducer 一致，不强加 receipt.Sequence==当前 QuerySequence。

永久隔离不能只接一个外部 err：应用事务回滚后，新的短事务重锁同一 Task/State/receipt，要求 recovery_version 和当次 evidence identity 均匹配，重新读取并按同一受支持 schema 解析当前 ObservationJSON。原始字段有任一变化时不使用旧诊断。该再次读取用于决定调度进度，不读取加密正文或上游 URL。

### 5.2 严格分类

| 当前锁内事实/错误 | 处理 |
| --- | --- |
| 同一受支持 schema1 的 ObservationJSON 稳定出现 json.SyntaxError / json.UnmarshalTypeError | 固定 `query_observation_invalid`；due=NULL；version+1；AppliedAt 保持 NULL，资金/原证据不动 |
| 任一错误树含 ctx.Canceled/DeadlineExceeded、DB/driver/authority 错 | 禁止永久隔离；可在仍有效的调用 ctx 内按当前 version 有界退避；真实返回安全错误+cause。调用 ctx 已取消不启动 detached 进度写 |
| 已应用、已删除/序号已陈旧 | 保留原 reducer 的幂等/墓碑/陈旧处理；隔离器本身不能冒充 reducer 写 AppliedAt |
| runtime/schema/账务版本未知，身份无法由受支持关系证明 | 不解释 JSON、不隔离、不退款；候选原支持边界优先。混合 ctx 错不能被 Unsupported 掩盖 |
| videobilling.ErrConflict | 保留原 settlement_conflict 的人工核对语义，due=NULL；不得重算价格或改已结算值 |
| 负 usage / 其它 ErrInvalid / FK 或唯一约束错误 / 缺依赖 | 不凭一个宽泛 sentinel 宣称永久；本批安全固定 `query_apply_failed` + DB now+30秒退避，保留真实错误。后续要永久化须另有锁内因果证明 |
| 空 Observation、unknown outcome、观察到错误 target/model | 继续原 reducer 的 observation_needs_review 等行为；不能把这批变成新一套供应商协议解析 |

固定 30 秒退避沿现 inbox 原则，不另加 attempts 列/指数重试策略。原始诊断 State.sync_state=needs_review 如需保留，与新进度一并在现有受支持锁序中写；不得用它当资金终态。成功应用与进度终止在原同一事务内提交；迟到错误在 AppliedAt 非空或 version 已变化时 no-op，不能降级。

COMMIT 结果不确定时保留证据且返回真实不确定错误；随后 current read 发现已 AppliedAt 即停止，不把未知提交当未提交再释放。提交成功后才发生 ctx 取消不得倒改已提交计数。

### 5.3 本片不交付解除，旧 sender 不能清屏障

NULL 隔离屏障在**普通 applyQueryReceipt 的锁内**也检查；只过滤 recovery SELECT 不够，旧 N sender 持有内存 receipt 的直接 apply 调用不能绕开。N−1 无该检查，见混跑边界。

本片不新增“强制忽略校验”管理员按钮，也不增加只有测试调用的复核权限 API。当前行为与后续边界为：

- 临时退避仅由主库时间到期自动再选，锁内重新校验，不修改证据。
- 当前仍是相同 malformed JSON 的永久 review 不允许解除；没有合法“重试一下就修好”的状态，不能为可操作性改原文。
- 若新的受支持有效 receipt 已使旧序号变陈旧，或任务已合法 tombstone，已处于 NULL 屏障的旧回执在 S1 仍保持 review。未来如交付受控复核，应持有 expected recovery_version、完整 receipt 身份，在相同锁序下确认终止事实并复用原 stale/deleted reducer；该入口和权限审计均不在本片。普通 sender 不能因序号已陈旧自动越过 NULL 屏障。
- 若未来引入新的受支持解析合同，必须有新 consumer/兼容契约；本片不能把 unknown schema 改成 v1 后重试。

主控已决定 S1 不暴露新的 HTTP 或内部通用解除入口；只实现正常发送者、恢复者都必须遵守的锁内屏障。测试通过实际已有 apply/recovery 入口证明不会清屏障，不创建测试专用授权通道。没有复核入口时如实报告“待人工核对，解除能力未交付”。任何普通调用者/旧 sender 都不能仅凭既有 error 值把 due 从 NULL 改为非 NULL。

### 5.4 旧固定诊断的窄兼容边界

保留既有 `create_identity_review`：本次已取得受支持 Task/State/receipt 当前锁与证据 token，新的诊断事务须按相同锁序再次确认真实 create quarantine，才可写旧固定码与既有 State.needs_review；due 保持非 NULL、以主库时间临时退避，version按已确认提交递增。若 quarantine 已消失，不沿用旧错误；此路径不得制造永久 NULL 或清除已有屏障。

保留既有 `runtime_contract_unsupported`，但不能为旧文案绕过未知合同。初次 Task→State current 锁已取得且合同结果是纯 Unsupported 时，继续锁精确 receipt；只有 receipt 自身为已知 V1/schema1、归属精确、未应用且 due非NULL，才从本次锁内真实行生成独立兼容 token。新短事务重复相同锁序与全部身份/immutable摘要/version/任务合同和快照ID，确认当前合同仍是纯Unsupported；DB、ctx、未知receipt格式、已应用、NULL或较新version均不能授权写入。此分支只写旧固定 ApplyErrorCode，不读/解析JSON，不改未知State、due、version或任何资金。它不经过普通progress的未知合同门禁，也不扩大恢复候选。

仅旧诊断码发生实际提交时计 Deferred，含义是诊断等待，明确不是新退避时间；已同码/成功胜出等无更新则不计提交动作。原Unsupported仍作为本次失败安全返回。受控解除能力仍未交付。

## 6. 零网络调度 API 与错误汇总

建议公开两个实际由 main 消费的入口：

```
ProcessPersistedEvidenceOnce(ctx context.Context) error
ProcessDispatchOnce(ctx context.Context) error
```

`ProcessOnce(ctx)` 保留旧组合供既有调用者及固定 harness，先 recovery 再原派发/查询；不要改变 processOperation/pollTask 的公共语义。main 使用两个入口，各自走现 `mainJobs.goRun → periodic → leader.IsLeader`，不再同时调组合入口。Dispatch 仍包括 create/cancel/delete 的最多20候选及普通GET最多40；本片不将 GET 移入“零网络恢复”。

恢复分四个有界 lane：create inbox（含其既有 expired register）、mutation inbox（同上）、legacy operations、query receipts。解开 recoverResponseInbox 对 mutation 的隐式串接；一个 lane 普通失败不阻止其它 lane 获得本轮机会。已有各 batch 上限不变，ctx 取消立即结束。

主控已批准待真实验证初值：整轮上限10秒，每lane独立最多2秒、单独进度/诊断事务1秒、clock SQL最多200ms并继承更早父期限。不能让第一lane吃光后面lane的全部预算；lane自己的期限结束只结束该lane并返回错误，parent取消则立即结束整轮。现 reducer 的业务事务不得被替换为跨域伪事务或异步悬空 goroutine；所有新 loop 都可取消/join。预算不够的未处理行留待下一轮，统计与错误如实返回，不把这些初值当成吞吐或500并发结论。

lane 返回内部摘要：Selected/Applied/Deferred/Review/Noop/Failed 计数及安全分类错误；不要暴露业务正文。整轮汇总为固定 Error()，内部 Unwrap 保留安全 error 链与 ctx cause；有失败就不能返回 nil，仅成功幂等/noop 可成功。Handled-review 可以独立计数，首次导致 review 的实际 apply 失败仍在本轮错误汇总中；之后它不再被每轮重复计为“成功恢复”。

统计含义：Selected 是实际候选数；Applied、Deferred、Review 只在相应数据库事务确认提交后计数，提交错误或结果不确定时不得猜测成功。Noop 是没有新提交动作的成功幂等/失权返回；nil 本身不是 Applied。Failed 是实际失败事件数，包含候选查询/存储失败：候选查询失败时 Selected=0、Failed=1，整轮 Errors 仍记录该错误；它也可与已提交的 Deferred 或 Review 重叠。因此这些字段不是互斥分箱，不满足 Selected=其余各列相加。读取已经存在的 NULL due 屏障只保留拒绝错误，不重复累计 Review，也不计成功 Noop。首次失败经安全退避或隔离后仍返回原错误；未处理候选不得计成功。

现 metrics.startCycle 需区分组合调用与单lane，避免 ProcessOnce 嵌套导致两次计数。指标标签只有固定 lane/result/code，不使用 Org/Task/Key/URL。日志最多固定安全 ID 和枚举；不能打印原错误、响应JSON、SQL或绑定值。

### 10.2 固定错误来源与分类顺序

- 包私有 sentinel `errQueryObservationInvalid` 的 Error() 为固定安全文案；其包私有 typed wrapper 只保存 `syntax` / `type` 枚举，不保留可能包含字段、值、JSON片段的 decoder Error() 文本。`decodeQueryObservation` 只有在真实 `json.Unmarshal` 得到 `*json.SyntaxError` 或 `*json.UnmarshalTypeError` 时构造该wrapper；其它错误不能转换为此sentinel。该函数仍使用原queryObservation结构，不扩协议。
- `recordQueryRecoveryFailure` 不能仅 `errors.As(cause, *json.SyntaxError)` 就隔离，也不能接受任意命中sentinel的合成错误作为授权。必须同时有锁内token、当前合同/身份一致、当前重新解码产生同一专用typed失败，才允许NULL；单次外部错误或已变化的JSON一律不能决定永久进度。
- 分类优先级固定：先检查parent/事务ctx和完整error树的DB/driver/authority或未知cause，再判专用JSON类型或既有settlement冲突。只接受本域私有安全汇总包装、直接专用JSON类型和直接既有settlement冲突；外部 errors.Join、fmt 包装及自定义 Unwrap 均按未知临时错误处理，不能剥离包装自身的未知语义。混合树含 canceled/SQL/unknown 时不得永久化，不依赖错误文本匹配。
- 原 `videobilling.ErrConflict` 的单一受支持路径沿现语义 `settlement_conflict`；混合DB/ctx错误不得被该sentinel掩盖。宽泛ErrInvalid、Unsupported、RecordNotFound均不能靠一次errors.Is升级为永久JSON。Unsupported/身份错误不解释JSON、不写永久progress。
- 安全返回error的 Error() 不插入原cause文本，内部 Unwrap 保留ctx/权威分类的errors.Is。日志只能用固定lane/disposition/code。不得把原JSON error保存到ApplyErrorCode或任何消息。

上述路线已获主控决策；固定N和隔离工作树已建立。现开始0133及query进度实现，其它lane/宿主由主控独立分派。没有上线或解除功能授权；S2独立财务恢复、HTTP窗口fence与500并发容量仍未完成。
