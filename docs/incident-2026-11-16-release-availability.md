## 新发布纪律

1. 仅允许**目标迁移与已应用迁移完全相同**的应用版本走自动发布。需要数据库迁移或边缘 Caddy 配置变更时，预检或部署提前拒绝；须先设计在线兼容迁移方案。
2. 在旧服务运行时完成加密备份、解密及校验、旧版与当前实际路由镜像归档、候选构建。备份失败不切流。在线备份是数据库一致性快照，不能代表停写后某个瞬间的全业务状态，因此不再做“停写最终备份”。
3. 候选 core 和静态前端以独立 Compose 服务加入现有内部网络，不绑定公网端口。先检查两容器健康和内部 `/healthz`、`/api/status`，并确认旧公网仍正常。
4. 仅在候选就绪后热加载 Caddy 路由。公网 `/healthz`、`/api/status`、`/` 任一失败时热恢复原路由；不停止公网 Caddy，不显示维护页。旧 core 保留运行，承接尚未完成的后台任务并供回退。
5. 切流后观察容器健康、健康接口、任务接入错误与资源指标。真实收费任务须另有授权和预算；本次发布流程优化不执行资金或收费冒烟。
6. 只要求目标 `main` 完整 SHA 的关联 CI 已提交、可查询并记录状态；不等待所有任务完成。已知失败须在发布记录中明确，不能伪称 CI 通过。

回退只热加载此前保存的真实 Caddy 配置，旧容器始终在运行。若候选自身健康但业务指标持续异常，应回退路由并保留诊断材料。
