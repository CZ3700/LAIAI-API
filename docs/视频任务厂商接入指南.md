# 视频/任务型厂商接入指南

> 适用范围：所有"提交 → 轮询 → 取产物"的异步生成型 API（视频生成、长耗时图像/音频任务）。
> 对应代码：`core/internal/task/`。对应设计：`整体架构设计.md` §4.4 Task API。
>
> 与 chat/embeddings/images/audio 这类**同步**模态不同，任务型是**双请求**模式（提交一个请求拿到
> upstream task id，再轮询查询直到终态），所以它走独立的 `task.Adaptor` 框架，不复用 relay 的 `adapterFor`。

---

## 一、框架已经替你做好的事（厂商适配器**不要**再碰）

接入一个新厂商，你**只**写"协议翻译"。下面这些资金与编排逻辑由 `task.Service`（`task.go`）统一保证，
适配器无权也无需介入：

- **计费快照**：提交时按 `EstimateOutputTokens` × 模型 `output_usd_per_1m` 估算并 `CreateHold` 预冻结；
  价格快照写进任务行（`price_out_usd_per_1m`），结算时**不读实时价**，防止改价污染在途任务。
- **并发闸**：渠道行 `FOR UPDATE` 串行化同渠道 Submit + 同事务重新计数 + 占槽，消灭 count-then-act 竞态。
- **终态结算**：成功 → `SettleHoldExact`（按上游真实 `completion_tokens`）；失败/超时 → `Release` 全退。
  转态 + 结算同一事务，`WHERE status IN (...)` 的 CAS 防双重结算（并发轮询里只有一个赢者结算）。
- **超时清扫**：超过 `TaskTimeout`（默认 30min，可配置）未终态 → 自动 failed + 全退，不留僵尸占住槽位。
- **org 隔离**：`Get` 强制 `org_id` 过滤（红线 5）。

也就是说：**资金安全、并发、超时、隔离都是框架的，适配器只负责把厂商方言翻译成本包的结构。**

## 二、三步接入

### 步骤 1：新建 `core/internal/task/<vendor>.go`，实现 `Adaptor` 接口

接口定义在 `volcengine.go`，5 个方法，全部是纯"协议翻译"（无副作用、无资金操作）：

```go
type Adaptor interface {
    // 给 hold 预冻结的输出 token 上界（保守取大；真实成本结算时按上游 usage 校正）。
    EstimateOutputTokens(model string, content []any) int64
    // 构造"提交任务"请求。content 是客户端原样透传的 content 数组（薄透传，不二次发明参数）。
    SubmitRequest(ctx context.Context, ch *relay.Channel, credential string, in SubmitInput) (*http.Request, error)
    // 从提交响应解析出"上游 task id"。非 2xx 或缺 id 必须返回 error（触发 release + 不留任务行）。
    ParseSubmit(resp *http.Response) (upstreamTaskID string, err error)
    // 构造"查询任务状态"请求。
    QueryRequest(ctx context.Context, ch *relay.Channel, credential string, upstreamTaskID string) (*http.Request, error)
    // 把上游查询响应归一到本包 QueryResult。
    ParseQuery(resp *http.Response) (QueryResult, error)
}
```

`ParseQuery` 返回的 `QueryResult`，其中 `Status` **必须**归一到本包四个常量之一：

```go
type QueryResult struct {
    Status           string // 必须是 StatusQueued / StatusRunning / StatusSucceeded / StatusFailed 之一
    ResultURL        string // 产物地址（视频/图片 URL）
    CompletionTokens int64  // 上游 usage；>0 时按它精确结算，=0 时框架按估算保守收并打 warn
    FailReason       string // 失败原因（落到 tasks.fail_reason，便于排障）
}
```

**状态归一规则（照抄 volcengine 的写法）**：
- 上游"排队"→ `StatusQueued`
- 上游"执行中"→ `StatusRunning`
- 上游"成功"→ `StatusSucceeded`
- 上游"失败 / 取消 / 拒绝"→ `StatusFailed`
- **未知状态保守按 `StatusRunning`**（下一轮再看，绝不误杀正在跑的任务）

> 凭证由框架解密后以明文 `credential` 形参传入；适配器只负责拼进 `Authorization` 头，**绝不**落库、绝不日志。

### 步骤 2：在注册表登记

打开 `volcengine.go`，在 `taskAdaptors` map 加一行（key = 渠道的 provider code）：

```go
var taskAdaptors = map[string]Adaptor{
    "volcengine": volcengineTask{},
    "modelark":   volcengineTask{},
    "<your-vendor>": <vendor>Task{},   // ← 新增这一行
}
```

如果新厂商复用某个已有"家族"（同一套 API 协议、不同 provider code），可不在此登记，改在
`relay/providers.go` 给该 provider 档案设 `Adapter: "<家族名>"`——`adaptorFor` 会先查 `taskAdaptors`
精确命中，未命中再按 provider 档案的 `Adapter` 家族回退一次。

### 步骤 3：🚨 红线 —— 用**真实上游 raw response** 写一次 fixture 测试再上线

这是不可跳过的硬性纪律（参见根目录工作准则"绝不编造"、epay 方言事故教训）：

- 真实调一次厂商的提交 + 查询 API，**抓原始 JSON**。
- 用真实响应做 fixture，断言 `ParseSubmit` 能取到 task id、`ParseQuery` 的 status 枚举/产物 URL/usage
  字段都对得上。
- **绝不**凭厂商文档臆造字段名/枚举值——文档与真实响应不一致是常态（epay 的 `trade_status` vs `status`
  方言就是文档没写、真实响应才暴露的）。

参考现有测试：`core/internal/task/adapter_test.go`（分发逻辑）。新厂商应再加
`<vendor>_test.go` 覆盖 `ParseSubmit` / `ParseQuery` 的真实 fixture。

## 三、定价前提

任务型按 `completion_tokens` 结算，复用 `model_prices` 表的 `output_usd_per_1m`。接入新厂商前确保：

1. 该厂商的模型已在 `model_prices` 有定价行（`output_usd_per_1m` 为正）。
2. 厂商的 `usage.completion_tokens` 与你的 token 口径一致；若厂商按"秒/帧/分辨率"计费而非 token，
   需要在 `EstimateOutputTokens` 与 `ParseQuery` 里把厂商单位换算成等价 token（并在该厂商文件注释写明换算依据）。

- [ ] credential 只进请求头，未落库未入日志。

- [ ] `<vendor>_test.go` 用**真实** raw response 做了 fixture 断言。
- [ ] 模型在 `model_prices` 有正定价；token 口径已核对/换算。
