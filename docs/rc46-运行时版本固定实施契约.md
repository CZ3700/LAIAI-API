# rc.46：视频运行时版本固定实施契约

状态：P0-1 v1 固定实现已开发，隔离 MySQL、真实旧二进制交接及 CI 验收进行中；尚未发布生产。多版本 Worker、V2 与 500 在途验收不属于本次完成声明。

实施基线：2026-10-26，main `ceecb121093610b8727808d63f1917492832f610`（PR #57），原迁移最大为 `0126_user_display_currency.sql`。本批新增 `0127_video_runtime_contracts.sql`；合入前仍复核 main 未占用该编号。

架构事实源为[整体架构设计](整体架构设计.md)，批次顺序见[分阶段执行与验收](rc46-seedance500-分阶段执行与验收.md)。本契约规定第一份独立 P0-1 PR 的实现与验收边界；不替换已存在的 Ark、Invocation Store、USD Decimal 账务或顺序 SQL 迁移。

## 1. 交付目标与限制

第一 PR 只注册当前官方 Ark 的 v1 兼容实现，使每个任务的协议解释、上游调用和账务解释固定下来。声明“支持旧 v1 与拒绝未知版本”需要完整入口验收，不能仅增加数据库列。

- 不开放 V2 任务，不让管理员填写任意版本，不加载 JavaScript 或远程插件。
- 不修改价格、汇率、最低用量、舍入、hold/capture/release 公式或客户授权上限。
- 不新增第二套任务或账本，不将 legacy `task` 路径作为官方 Ark 的版本回退。
- 不在这一 PR 改租约时钟、fence、Operation 行版本语义或迟到响应收件箱。
- 不因运行时不支持、版本为空、查询失败、租约到期而退款、重发或伪造终态。
- 生产仍按已验收镜像 digest 部署；本契约通过不代表 500 并发已达标。

| `video.QueryReceipt` / `video_query_receipts` | 归一化观察、响应证据、序号、应用结果 | 保存生产该观察的契约身份及观察数据格式版本 |
| `invocation.VideoPayload` | 加密数据格式 `SchemaVersion`、purpose、组织隔离、读取审计 | 保留独立格式语义，执行输入与产物解码按固定协议实现处理 |

| 发布制品 | source commit 与镜像 digest | 验收记录支持的契约组合和 descriptor hash，不反填虚构的历史镜像 |

`UsageEvidence.SourceVersion` 目前是某来源证据的版本/身份（查询路径使用 attempt），不能改作 adapter 或账务 schema。类似地，`Operation.Version`、`State.RowVersion`、`QuerySequence` 均不承担运行时选择职责。

## 3. 固定契约及版本注册

### 3.1 第一 PR 的唯一兼容组合

以下是本批实现的固定命名，尚未登记到生产数据库：

| 维度 | v1 兼容标识 | 约束内容 |
| --- | --- | --- |
| runtime | `ark-official-legacy-v1` | 任务宿主、状态推进、取消/删除及证据应用的兼容行为 |
| adapter | `ark-v3-v1` | 已验证模型的参数规范化、官方请求构造、响应解析与安全错误分类 |
| protocol contract | `video-contract-v1` | 内部标准 DTO、执行输入、typed receipt、产物投影的解释契约 |
| billing schema | `usd-decimal-v1` | 当前 USD Decimal 用量结算、冻结上限、成本与差额记录语义 |

注册器为编译期 Go 注册，按完整四元组精确解析。单个字段为空、未知，或四个已知字段组成了未登记组合，均返回安全错误 `runtime_contract_unsupported`。禁止把空串或未知值解释成 current/latest；禁止匹配不到时返回默认 OpenAI/legacy Task 适配器。

每项 descriptor 列出支持的动作、执行输入/观察/产物格式版本及稳定摘要。registry 不拥有数据库、凭据、网络、重试或资金。宿主继续负责这些边界。第一 PR 只有一个受支持组合，不通过两个不同版本字符串指向同一实现来冒充 N/N-1 验收。

runtime 版本是语义兼容身份，不等于 build SHA。同一契约可由多个安全补丁镜像支持；发布记录绑定 `source commit + image digest + supported contracts + descriptor hash`。历史任务没有记录生产镜像时保留“未知历史 build”，不得用当前镜像 digest 充作原始事实。

### 3.2 数据模型增量

| 表 | 拟增字段 | 写入时机及不可变规则 |
| --- | --- | --- |
| `video_task_states` | `runtime_version`、`adapter_version`、`protocol_contract_version`、`billing_schema_version`，各 `VARCHAR(64)` | 与任务/冻结同事务创建；任务存续期间不随配置更新改写 |
| `video_billing_snapshots` | `billing_schema_version VARCHAR(64)` | 与现有快照同事务创建；必须与 State 一致 |
| `video_operations` | `runtime_version`、`adapter_version`、`protocol_contract_version`，各 `VARCHAR(64)` | 操作创建时从任务固定身份复制；记录发送与解析身份，不从活动配置重建 |
| `video_query_receipts` | `runtime_version`、`adapter_version`、`protocol_contract_version`，各 `VARCHAR(64)`；`observation_schema_version` | HTTP 前捕获支持的身份，收到响应后按该身份保存观察；旧 receipt 登记为兼容格式 1 |

新增字段采用 expand-only SQL；保留原表、主键、幂等键和所有金额。索引必须针对实际候选 SQL 用隔离 MySQL `EXPLAIN` 验证；不得只给状态表加索引却让回执恢复全表排序。字段名及索引若在代码评审中调整，须同步本文与迁移测试，不引入隐藏 fallback。

版本字符串使用 `utf8mb4_0900_bin` 的大小写敏感、NO PAD 比较；尾空格也属于不支持版本，防止 SQL 把它选入候选而 Go 再拒绝。当前索引为 `idx_video_runtime_poll`、`idx_video_runtime_operation`、`idx_video_runtime_receipt`，另以 `idx_video_runtime_pending_usage` 支撑未结算版本阻塞观测。

唯一 descriptor 的 SHA-256 为 `77f6aa32417500ddd9e3e11a2a1036866cdda49237d86b7379ca67b92710f8bc`，动作含 create/query/cancel/delete/delivery_refresh，执行输入、观察与产物格式均为 1。`ReadForExecution` / `ReadForDelivery` 的兼容签名明确使用 v1；新执行路径使用带预期 schema 的 API。历史/恢复证据读取保持原样，不把未解释原文当作可执行数据。

执行输入元数据在 claim、本地取消、确定未发送释放及发送前检查，并核对 Operation 与 State 的输入引用一致。未知格式即使同时过期、素材校验失败或预算阻断，也不能进入自动退款。合法 v1 过期仍由原有确定未发送语义处理。

## 4. 入口覆盖清单

| 入口 | 必须采取的行为 | 未支持版本时 |
| --- | --- | --- |
| `Service.plan` / `Estimate` / `EstimateForKey` | 报价使用注册器允许的新受理组合；保持当前能力与价格验证 | 冻结前明确拒绝，不给不可执行版本报价 |
| `Service.Create` | 在受理事务写完整 State、Snapshot 和 create Operation 版本；重复幂等请求仍返回原任务 | 不创建任务、不产生单边冻结/预算 |
| `pendingOperationCandidates` / `pendingQueryCandidates` | SQL 在 LIMIT 前排除不支持组合；真正 claim 时再次检查 | 不消耗候选批次，不发 HTTP；单独统计待兼容处理数量 |
| `processOperation` / `processMutation` / `pollTask` | claim 前解析固定版本，保留原版输入、模型、账户和凭据绑定；发送前继续现有 claim 复核 | 保留原状态、资金及上游占用，不自动切渠道或换版本 |
| `clientFor` | 按固定组合构造受控官方客户端；凭据仍来自任务快照 | 返回独立可识别错误，不能混入 credential_unavailable 退款路径 |
| `persistResponse` / 查询响应落库 | 使用 HTTP 前捕获的生产者契约保存证据；不要求当前活动 registry 支持应用 | 先保留证据，暂停应用，不能直接丢响应 |
| `recoverOperations` / `recoverQueryReceipts` | 支持组合检查与候选过滤覆盖恢复路径；unknown 创建依旧不重新 POST | 不写应用完成标记、不按时间退款；可恢复处理不被未知版本头部阻塞 |
| `applyCreateReceipt` / `applyMutationReceipt` / `applyQueryReceipt` | 核对任务、操作/回执的契约和 schema，按固定实现处理 | 不推进生成状态、不动账、不填 `ReceiptAppliedAt` / `AppliedAt` |
| `SettleUsageTx` / `ReleaseConfirmedTx` | 在已锁定 Snapshot 边界校验 billing schema，调用侧核对 State/Snapshot 一致 | 拒绝资金写入，证据保留 |
| `SettleBillUsageTx` / 调整提案与应用 | 独立对账也执行同一账务 schema 保护，不借导入绕过 | 账单原始记录仍可保留，对应结算/调整待兼容处理 |
| `Cancel` / `Delete` | 按固定运行时解释准入及本地取消行为，创建操作时继承身份 | 不生成未知语义的操作、不错误释放冻结 |
| `prepareDelivery` / `readDelivery` / `refreshDelivery` | 已保存胶囊按固定格式读取；刷新调用同一版本客户端 | 不对上游另行 GET、不用最新版解析旧任务；明确显示产物暂不可解析 |
| 任务列表、日志、账单历史读取 | 组织隔离下仍返回不依赖未知解释器的持久投影 | 不将整个历史详情变成 500，不隐藏原账务记录 |

特别注意：当前 create 在 `clientFor` 出错时会调用 `knownUnsent(..., "credential_unavailable")`。因此只在 `clientFor` 添加 registry 校验是不合格实现。版本拒绝必须先于 claim，并以独立错误路径退出；防御性复核也不得降级为确定未发送证据。

## 5. 证据保存与应用分离

执行者在 HTTP 前捕获固定契约，客户端构造、响应解析及 receipt 写入使用同一个值。配置发布或其他节点升级不能改变已发送请求的解释身份。

有两种不同的“未知”，必须保持区别：

1. `submission_unknown`：上游是否创建未知，但任务可以属于已知 v1 契约。保留原有回执恢复与人工核对，不重新 POST。
2. `runtime_contract_unsupported`：当前进程没有相应实现。任务/原始证据仍存在，暂停派发或应用，等待兼容进程；不把它转换成失败、取消或零费用。

新加入的版本检查不得挡在已发送回执的持久化之前。若响应已保存、应用阶段不支持，记录安全阻塞原因但保留未应用标记；恢复兼容实现后按原幂等键应用一次。只读历史与聚合指标不得输出 raw response、请求正文、凭据、签名 URL 或跨组织资源标识。

**本 PR 不宣称解决完整迟到证据问题。** 当前 `persistResponse` 把证据写入和 Operation 的 version 条件更新放在同一事务；如果该条件更新失败，证据也会回滚。PR #56 的租约恢复不增加 Operation version，所以既有“同 attempt 租约过期后迟到响应”可恢复测试通过；这不等于任意旧 fence/不同 attempt 回执都会被保存。不可变 inbox、late-attempt 归属及数据库时间租约属于 P0-2，须独立设计、实现和故障验收。第一 PR 不增加新 fence，也不通过删除 CAS 换取表面上的“回执不丢”。

## 6. 迁移、旧二进制与发布顺序

1. 合入前核对最新 main 的迁移序列、State/Operation/receipt 行数、未终态与 pending_usage 数量。无运行时字段的旧行不能根据创建时间或当前价格猜测版本。
2. 对历史官方 Ark 行显式登记上述 legacy-compatible-v1 组合，来源注明“迁移兼容归类”。该标签承诺新实现兼容旧行，不声称已经获知原始 build。保留 unknown、空 upstream ID、冻结与全部回执，不改数据使其看似成功。
3. 新列在兼容过渡期使用明确的 legacy v1 默认值，以允许旧二进制省略这些列继续写入。新二进制必须显式写完整组合；新代码写空串不能靠应用 fallback 变成 v1。
4. 先完成 expand migration，再部署只支持/只写 v1 的版本感知 API/Worker。迁移前后跑同组旧任务恢复及资金核对；禁止在该批引入 V2。
5. 旧二进制不识别运行时过滤，它会领取新版本任务。只要还有旧 API/Worker/恢复 job，就必须保持新受理 v1；不能因某个新节点已支持 V2 就打开 V2。
6. 将来启用 V2 前，必须证明全部领取器和所有结算/产物入口已版本感知，旧实例清单为空或在受控兼容池；落实完整 P0-2 后再评估新派发逻辑。
7. v1-only 阶段回退到旧二进制仅限确认所有任务仍为 v1 且未引入新语义的受控回退。实际产生 V2 后禁止回退到不识别版本的二进制；先关闭新受理、保留兼容 Worker 排空。不得恢复旧数据库备份抹掉新任务/账务。

字段回填和默认值不等于任务已经排空。待结算、unknown、产物刷新及待应用 receipt 也纳入旧版本保留条件。

## 7. N/N-1 兼容矩阵与证据

| 执行进程 | 任务/回执版本 | 预期行为 | 第一 PR 状态 |
| --- | --- | --- | --- |
| 旧非版本感知进程 | 仅 legacy v1 | expand schema 下原路径继续运行；禁止出现 V2 | 必测过渡组合 |
| 新版本感知进程，仅编译 v1 | 迁移归类 v1、新写 v1 | 完整查询/取消/删除/结算/产物兼容 | 必测 |
| 新版本感知进程，仅编译 v1 | 空版本、未知版本、字段组合不一致 | 零上游调用、零资金变动，证据不标已应用 | 必测 |
| N+1 进程显式编译 N 与 N+1 | N 在途任务、N 回执 | 按 N 的实现处理，不重新定价、不重发 | 未来 V2 前必须完成；首批不能标已通过 |
| 仅 N+1 进程 | N 任务 | 不领取、不默认套用 N+1；告警并由保留的 N Worker 处理 | 未来版本退役门槛 |
| N Worker 与 N+1 Worker 并存 | 各自支持的任务 | 同作用域容量与资金幂等仍共享；无双发 | P0-2/P0-3 验收，不由版本字段自行保证 |

N/N-1 测试必须使用两个实际不同的实现/镜像或明确保留的版本实现。相同代码换版本字符串、仅验证 registry map 可查找，不能证明滚动升级兼容。

## 8. 第一 PR 的测试与完成标准

使用隔离真实 MySQL 8.4、合成/脱敏 fixture、Mock HTTP，禁止生产凭据与付费生成。每项记录 source SHA、migration、工具链、镜像、contract descriptor hash、命令/退出码和没有跳过的测试结果。

| 验收项 | 必须断言 |
| --- | --- |
| 迁移、重放与旧写入 | 已有行明确归类 v1；旧列省略写入正常；新代码空串拒绝；原金额/账本/任务状态不变；schema-doctor 无漂移 |
| 受理与幂等 | State/Snapshot/Operation 身份同事务固定；重复请求返回原身份；版本错误无单边冻结 |
| 配置更新隔离 | N 任务受理后修改活动配置，执行输入、上游模型、契约、价格与 FX 不变 |
| 全入口拒绝 | 未知/空/不一致组合覆盖 create/query/cancel/delete、delivery refresh、回执恢复、对账；HTTP 调用与资金变动均为零 |
| 候选公平 | 超过一批的 unsupported 行、有效租约行排在前面时，后面的受支持任务仍被选中；查询有界 |
| 已发送后暂不支持 | 回执按生产者身份保存、不应用、不退款；恢复支持后只应用一次且不再 POST |
| 历史特殊状态 | accepted、submission_unknown、成功缺 usage、已结算、软删除、待恢复 receipt 分别验证；显式零和缺失保持区别 |
| 账务旁路 | 直接 SettleUsage/Release、账单结算与调整均拒绝未知 billing schema，原证据和冻结仍可查 |
| 产物读取 | 已知 v1 胶囊继续可读；未知 schema 不用最新解析器猜读，不触发额外官方 GET |
| 权限与证据 | 跨组织拒绝；日志与观测不含正文/凭据/URL；错误码不暴露其他租户的运行时记录 |
| 旧版本回退演练 | v1-only 阶段真实旧镜像与新 schema 兼容；演练报告明确 V2 尚未开放 |

原有 `make vet`、`make ci`、真实 MySQL、race 与迁移门禁继续执行。新增测试未提供 `ARK_TEST_MYSQL_DSN` 而跳过时，不能计为通过。

`make ark-runtime-compat` 使用固定旧提交 `ceecb121093610b8727808d63f1917492832f610` 的真实业务代码，仅叠加同一个测试 harness；分别编译旧、新二进制。在迁移前及 expand 后各由旧二进制创建四类任务，再由新二进制恢复两批未应用回执，验证无新 HTTP、每个待结算任务仅结算一次。runner 拒绝外部 DSN，只清理本次标签匹配的专用 MySQL，记录源码与二进制摘要、三阶段无 skip 结果。该命令通过才可登记旧二进制兼容，不能以本地无 DSN 的单测跳过代替。

完成声明限于：“现有 v1 任务契约固定，未知版本不执行、不动账，旧任务可兼容恢复”。独立 Worker、数据库时间、完整 fencing/inbox、多版本生产并行、500 在途和真实上游容量均保留在对应后续批次，按各自证据验收。
