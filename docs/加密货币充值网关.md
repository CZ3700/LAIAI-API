> 三档：**通用 CryptoGateway 骨架**（处理商无关、admin 后台热接入，推荐路径）+ **Coinbase Commerce**（托管型）
> + **x402**（agent-native 链上微支付）。三者都默认**禁用**，验真后才进真金路径（与 EPay/Stripe 资金红线一致）。

## 〇、通用 CryptoGateway（推荐：admin 后台灵活热接入，处理商无关）

`core/internal/payment/crypto_gateway.go`：一个**处理商无关**的加密货币网关骨架，适配主流
「托管发票 + HMAC 签名 webhook + 状态查询」三段式处理商（EBPay / OxaPay / NOWPayments / Cryptomus / Plisio 这一类）。

**热接入（无需改代码、无需重启）**：在 admin 后台「支付渠道」新建一个 `protocol=crypto` 的渠道，config 填：

```
processor      ebpay              # 处理商标识（仅日志/区分）
api_base       https://...        # 处理商 API 基址
api_key        <商户 key>
webhook_secret <验签密钥>          # 部分处理商 == api_key
sign_algo      sha256             # 或 sha512（webhook HMAC 算法）
create_path    /payment           # 创建发票端点（默认 /payment）
query_path     /payment/          # 查状态端点（默认 /payment/{order}）
```

保存（AES 加密入库）→ **enabled 由 admin 验真后手动开**。入金完全复用 `creditPaidOrder` 幂等
（`topup:<order_no>`）+ `ReconcileTopups` 主动对账，零新增入金代码。

**为何安全（即便误启用也不致误入金）**：验签 **fail-closed**（签名口径不符→拒所有 webhook）；
金额取**实付**（`amount_paid`），underpaid 被「实付不得少于应付」拦；仅
`paid/confirmed/completed/finished/success` 终态入金，绝不在 `pending` 入金。

**🚨 上线某真实处理商前必须验真**（红线，绝不凭文档臆造）：接其真实环境抓 raw webhook + create 响应写
fixture，校正：① 签名口径（部分处理商如 Cryptomus 用 `md5(base64(body)+key)` 的排序参数方案，需在
VerifyCallback 特化）；② create 响应里支付页/地址字段；③ webhook 里 `order_no`/实付金额/成功状态枚举。
已测（合成 fixture）：HMAC 验签往返 / 伪造拒绝 / underpaid 返实付 / pending 不入金 / data 包裹解析 / sha512。

## 一、Coinbase Commerce（托管型「加密版 Stripe」）

> 两者都默认**禁用**，验真后才进真金路径（与现有 EPay/Stripe 的资金红线纪律一致）。
> 调研依据：行业横评（Coinbase Commerce / NOWPayments / BitPay / 链上直收 / x402）选定托管型为主——
> 商户不托管私钥、不跑链上节点、与现有 hosted-redirect+webhook 架构同构、合规面最小。

---

## 一、为什么选 Coinbase Commerce 做主通道

| 维度 | Coinbase Commerce | x402 | NOWPayments |
|---|---|---|---|
| 形态 | hosted_url 跳转 + webhook + 查单 | HTTP 402 头 + 前端钱包签名 | hosted/API + IPN |
| 私钥/节点 | 商户都不需要 | 不需要（facilitator 结算）| 不需要 |
| 主动对账（QueryOrder）| ✅ GET /charges | ❌ 无标准异步查单 | ✅ |
| 验签 | HMAC-SHA256(raw body)，**同 Stripe** | EIP-3009 链上签名 | ksort+HMAC-SHA512（字节序敏感，易踩坑）|
| 接入风险 | 低（与本仓 Stripe 验签同构）| 中（依赖前端钱包）| 中（验签陷阱，需真实 IPN 样本）|

Coinbase 与现有 `payment.Engine`（CreatePayment/VerifyCallback/AckBody/QueryOrder）一一对应，
入金完全复用唯一资金路径 `creditPaidOrder`（幂等键 `topup:<order_no>` + 接受 pending|expired +
币种/金额校验 + provider 匹配），以及 `ReconcileTopups` 主动对账兜底——零新增入金代码。

NOWPayments 作为「币种覆盖」的二期补充通道（拿到真实 IPN raw 样本后再加一个 Engine 即可）。

## 二、代码落点（已实现）

- `core/internal/payment/coinbase_commerce.go`：`CoinbaseCommerce` 实现 Engine 5 方法。
  - 验签 = HMAC-SHA256(**raw body**) → hex，与 `X-CC-Webhook-Signature` 常数时间比对
    （据官方 coinbase-commerce-node/Webhook.js 源码，**已确认**）。
  - 成功态 = `charge:confirmed` / `charge:resolved`（绝不在 pending/delayed 入金）。
  - 已测：验签往返、篡改拒绝、成功态映射（`coinbase_commerce_test.go`）。
- `core/internal/server/payment.go`：`engineFor` 加 `coinbase` 分支，**门控 `coinbase_enabled="true"`**。
  settingDefaults 增 `coinbase_enabled / coinbase_api_key / coinbase_webhook_secret`。
- `core/internal/payment/x402.go`：`usdcAtomic` 改 Truncate（防向上取整要求多付）。
